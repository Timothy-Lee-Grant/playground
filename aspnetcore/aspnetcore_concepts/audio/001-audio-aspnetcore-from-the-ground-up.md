## Part one: what ASP.NET Core is, and what's in the repository

Start with the problem. A program that serves web requests has to do a long list of jobs that have nothing to do with its actual purpose. It has to open a network socket and accept connections. It has to speak HTTP, including the newer binary versions of it, HTTP/2 and HTTP/3. It has to handle encryption for HTTPS. It has to read headers and bodies safely, without letting a malicious client exhaust memory. Then it has to decide which of your functions should handle each request, turn the request's pieces into your function's parameters, and turn your function's result back into bytes. And around all of that: logging, configuration, security, error pages, compression, caching. ASP.NET Core does all of those jobs so your code only has to say what should happen for each kind of request.

The key idea of this part: **ASP.NET Core is a framework, not a library.** The difference is about who calls whom. With a library, your code is in charge: you call the library when you want something, and it returns. Your dotnet slash iot work is like this. Your program creates a GPIO controller and calls its methods, and nothing in that library takes over your program. With a framework, the framework is in charge. It owns the main loop and calls your code at the moments it chooses. When your app calls app dot Run, your main thread hands control to ASP.NET Core, and from then on ASP.NET Core accepts connections and calls your handlers whenever requests arrive. That handover is called inversion of control.

Let me bound that, because generalizations about this tend to get stretched. Inversion of control describes the relationship between your code and the framework's main loop. It doesn't mean every type in the repository is "a framework". Inside ASP.NET Core, plenty of pieces are ordinary libraries that the framework's own code calls, like the class that parses URLs, or the class that encodes HTML. And it doesn't mean your code never calls ASP.NET Core directly. In the builder phase you call its setup methods constantly. The inversion happens at one moment: when you call Run.

Now, what is in the repository? It's large, so here's the shape. At the bottom is **Kestrel**, the built-in web server, which owns sockets and speaks HTTP. Next to it are two Windows-only servers, HTTP.sys and the IIS integration, which you'll rarely touch. Above the servers is **hosting**: the code that starts the app, builds the pipeline and connects it to the server. Then **the HTTP abstractions**: the request object, the response object, and the interfaces underneath them. Then **routing**, which matches a request to the code that should handle it. Then the **middleware** folder: dozens of ready-made pipeline pieces, like HTTPS redirection, static files, compression, CORS, rate limiting and output caching. Then **security**: authentication, authorization, cookie handling. Then the programming models that sit on top: **minimal APIs**, where you map a URL straight to a function; **MVC**, with controllers and views; **Razor Pages**; **Blazor**, for interactive web user interfaces written in C#; **SignalR**, for real-time two-way messaging; and **gRPC** support. Plus **Identity** for user accounts, **Data Protection** for encrypting things like cookies, **OpenAPI** document generation, **project templates**, and some command-line tools.

What's **not** in the repository is just as important, because you'll go looking for it and not find it. The general-purpose building blocks that ASP.NET Core uses, dependency injection, configuration, logging, the options pattern and the generic host, are not here. They're the packages whose names start with Microsoft dot Extensions, and they live in the dotnet slash runtime repository, alongside the base class library. They're used by every kind of .NET app, not just web apps, which is why they live lower in the stack. So if you find a bug in how the dependency injection container builds objects, the fix goes to dotnet slash runtime, not here. Entity Framework Core, the database library, lives in dotnet slash efcore. The documentation you contributed to lives in dotnet slash AspNetCore dot Docs. And YARP, as you know, lives in dotnet slash yarp, built on top of everything in this episode.

A common misconception is that "ASP.NET Core" and "ASP.NET" are the same thing with a version bump. Actually, the old ASP.NET, the one tied to Windows and a component called System dot Web, is a different code base that's in maintenance. ASP.NET Core was a ground-up rewrite, released in 2016, cross-platform and open source from the start. When people today say "ASP.NET" casually, they almost always mean ASP.NET Core.

Recap of part one. ASP.NET Core is a framework: after Run, it owns the main loop and calls your code. Its repository holds the servers, hosting, HTTP abstractions, routing, middleware, security, and the programming models from minimal APIs to Blazor. The Microsoft dot Extensions building blocks, like dependency injection and configuration, live in dotnet slash runtime, not here.

## Part two: where the code comes from when your app runs

This part is about a layer you've said feels fuzzy: how code written by Microsoft ends up running inside your process. There are four different words involved, package, assembly, namespace and framework reference, and they're four different things.

An **assembly** is a compiled file, a dot DLL. It holds compiled code in a CPU-neutral form called intermediate language, or IL. When your app runs, the runtime's just-in-time compiler turns that IL into machine code for whatever CPU it's on. That's why the same DLL runs on your MacBook and on a Raspberry Pi. In the ASP.NET Core repository, nearly every project folder produces one assembly, and the project file is named after the assembly. The project for HTTPS redirection, for example, produces an assembly called Microsoft dot AspNetCore dot HttpsPolicy.

A **namespace** is just a naming prefix inside code, like a folder name for types. The using directive at the top of a C# file, for example "using Microsoft dot AspNetCore dot Http", only lets you write HttpContext instead of the full name. A common misconception is that the using directive gives your code access to a package or a library. Actually, it grants nothing. Access comes from your project referencing the assembly. The using directive is purely a shorthand for names that are already reachable. Remove it and the code still works if you spell out the full names; add it without the reference and the code still fails to compile.

A **NuGet package** is a zip file used to deliver assemblies, plus metadata, to a project that asks for them. Your project file lists a package reference, and at build time the tooling downloads the package and hands its assemblies to the compiler.

Here's the part that surprises people. **Most of ASP.NET Core does not reach your app as NuGet packages at all.** It arrives as a **shared framework**. When you install the .NET runtime on a machine, you also get a folder of ASP.NET Core assemblies, installed once, shared by every app on that machine. Its official name is Microsoft dot AspNetCore dot App. Your web project's first line says its SDK is Microsoft dot NET dot Sdk dot Web, and that SDK quietly adds what's called a framework reference to Microsoft dot AspNetCore dot App. At build time, the compiler is shown the shared framework's reference assemblies. At run time, the runtime loads the real ones from the machine's install folder. No NuGet download happens for any of it. You can see this on your own Mac later: the command dotnet, dash dash list dash runtimes, lists one line for Microsoft dot NETCore dot App and one for Microsoft dot AspNetCore dot App, each with a version.

Why build it this way? Three reasons. Every app on a server shares one copy on disk. Microsoft can ship a security patch once, by updating the runtime, and every app picks it up on restart, without being rebuilt. And it enforces discipline: everything in the shared framework must be supported for years, must not have third-party dependencies, and must not break compatibility in a patch. The repository's own guidance says exactly that.

You can see this in the repository. A project file that sets a property called IsAspNetCoreApp to true is a member of the shared framework. The HTTPS redirection project sets IsAspNetCoreApp to true and sets IsPackable to false, which means it ships only inside the shared framework and is never published as its own NuGet package. Other projects, like the test helpers or the OpenAPI support, are published as ordinary NuGet packages instead, because they're optional or move faster.

There's one more pattern you'll see on almost every page, and it's worth naming: **the abstractions split**. Many areas come as two or three assemblies. For example, there's Microsoft dot AspNetCore dot Http dot Features, which holds only interfaces describing what a server can provide. There's Microsoft dot AspNetCore dot Http dot Abstractions, which holds the abstract HttpContext class that your code programs against. And there's Microsoft dot AspNetCore dot Http, which holds the concrete DefaultHttpContext that actually does the work. The reason is to let other code depend on the contract without dragging in the implementation. A middleware author only needs the abstractions. A server only needs the feature interfaces. Only the hosting layer needs to know about the concrete class. When you see a folder whose name ends in dot Abstractions, the key idea is: **contracts live here; the code that fulfills them lives next door.**

Finally, solutions and processes, since this was also fuzzy. A solution is just a list of projects for your editor; it has no meaning at run time. A project produces one assembly. Only an executable project produces a program you can start as a process. A class-library project, which is what almost every project in this repository is, never runs on its own: its code runs inside whichever process loads it. So all those shared-framework assemblies run inside your app's process. And when you run the repository's tests, the test runner starts a process and loads the test assembly and the product assemblies into it.

Recap of part two. An assembly is a compiled DLL of CPU-neutral IL. A namespace is a naming prefix, and the using directive only shortens names. A NuGet package is a delivery zip. Most of ASP.NET Core arrives as the shared framework, Microsoft dot AspNetCore dot App, installed once per machine and selected by the Web SDK, not downloaded as packages. Abstractions assemblies hold contracts; the implementation lives next door. Library projects run inside whatever process loads them.

## Part three: the C# you'll read on every page

Before going inside the framework, let's make five pieces of C# precise, because the repository uses all of them constantly and several have no counterpart in C. For each one, here's what it is, what the compiler turns it into, and what it does not do.

The first is the **extension method**. When you write app dot UseHttpsRedirection, it looks like you're calling a method that belongs to the app object. You're not. UseHttpsRedirection is a static method in a separate static class called HttpsPolicyBuilderExtensions, and its first parameter is marked with the keyword this. That marker tells the compiler: allow callers to write this method as if it were a member of the first parameter's type. So the compiler rewrites "app dot UseHttpsRedirection, open-close parentheses" into "HttpsPolicyBuilderExtensions dot UseHttpsRedirection, with app passed as the argument". The key idea is: **an extension method is an ordinary static function with nicer call syntax.** What it does not do: it doesn't add anything to the class, and it gets no special access to the object's private fields. It can only use what's public. In C terms, this is exactly a function that takes a pointer to a struct as its first argument; C# just lets you write the call with a dot. Nearly every "Add something" and "Use something" method you've ever called in startup code is an extension method, and that's how every area of the repository plugs itself in without the core types knowing about it.

The second is the **lambda**, written with the arrow, an equals sign followed by a greater-than sign. When you write "context, arrow, context dot Response dot WriteAsync, of the string hello", you're writing a small anonymous function: on the left of the arrow are its parameters, on the right is its body. The compiler turns it into a real method with a hidden name, and then creates a **delegate** object that points at that method. You already know delegates from your events lecture: a delegate is an object that holds a reference to a method, plus, if the method needs one, the object to call it on. In C, the nearest thing is a function pointer, and the comparison is fair as far as it goes. Where it stops: a lambda can use variables from the surrounding method, and the compiler keeps those variables alive by moving them into a hidden object that the delegate holds on to. That's called a closure, and C function pointers have nothing like it.

You'll meet two delegate types everywhere in this repository. **RequestDelegate** is a delegate type that takes an HttpContext and returns a Task. It's the single most important type in ASP.NET Core: every piece of the pipeline, and every endpoint, is ultimately a RequestDelegate. And **Func**, F-U-N-C, is the general-purpose delegate type: Func of A and B means "a function that takes an A and returns a B". So when you see Func of RequestDelegate and RequestDelegate, read it as "a function that takes the next step of the pipeline and returns a new step that wraps it". Keep that phrase in mind; it comes back in part four.

The third is **generics**, the angle brackets. IOptions of HttpsRedirectionOptions, written with the type name inside angle brackets, means "the options interface, specialized for HTTPS redirection options". A generic is a type or method with a placeholder for another type, filled in at the point of use. Unlike C macros, the compiler checks every use, and the runtime creates real specialized code. When the dependency injection container is asked for IOptions of HttpsRedirectionOptions, it's being asked for a specific, distinct type.

The fourth is the **null-handling operators**, which the repository's style guide requires. Let me expand each one into the if and else it stands for, because "works like C's" isn't true for any of them. The question-mark-dot operator, as in "endpoint question-mark-dot RequestDelegate", means: if endpoint is null, the whole expression is null; otherwise, read endpoint's RequestDelegate. Written out, that's "if endpoint is null, the result is null, else the result is endpoint dot RequestDelegate". The double question mark, as in "a, question-question, b", means: if a isn't null, the result is a; otherwise the result is b. And the repository's style is to write null checks as "is null" and "is not null" rather than with double-equals, because "is null" can't be changed by a type that customizes the equals operator. One more piece: a type name followed by a question mark, like "string question-mark", means "this variable is allowed to be null". The compiler then warns you if you use it without checking. A plain "string" means "never null", and the style guide says to trust that and not add redundant checks.

The fifth is **async and await**, which you'll see in nearly every method. This gets its own part later, so here's just the outline. A method that returns a **Task** is promising "I'll finish later; here's an object you can use to find out when". The keyword **await**, placed in front of a Task, means: if the work is already done, keep going; if it isn't, return to my caller right now, and arrange for the rest of this method to run when the work finishes. The compiler rewrites an async method into a small state machine to make that possible. The key idea: **await doesn't block the thread and doesn't create one; it parks the rest of the method until the result is ready, and frees the thread to do other work in the meantime.**

One last piece of syntax you'll see on nearly every method body: the arrow is also used for a method whose body is a single expression. "Public int Count, arrow, underscore items dot Count" just means a method or property that returns underscore items dot Count. That arrow is the same symbol as in a lambda, but here it's simply a shorter way to write a body with one return statement.

Recap of part three. Extension methods are static functions with dot-call syntax and no special access. Lambdas create delegate objects and can capture surrounding variables, which C function pointers can't. RequestDelegate takes an HttpContext and returns a Task, and Func of RequestDelegate and RequestDelegate is "a function that wraps the next step". Generics are checked placeholders for types. Question-mark-dot and double question mark are compact if-else expressions about null. Await parks the rest of a method without blocking a thread.

## Part four: startup, and what builder, build and run really do

You know the shape: create a builder, register services, call Build to get the app, add middleware and endpoints to the app, then call Run. Now let's see what each step does inside the framework, and introduce the first characters.

The first character is **the Stage Manager**. That's the **host**, specifically the .NET Generic Host from Microsoft dot Extensions dot Hosting. The Stage Manager doesn't know anything about HTTP. Its job is to own the app's shared infrastructure, meaning configuration, logging and the dependency injection container, and to start and stop a list of long-running background jobs, called hosted services, in order. A web app is a host with one special hosted service added: a class called GenericWebHostService, which is the web part of the show. A worker app that only processes a queue uses the very same Stage Manager without any web part. That's the reason the host lives in dotnet slash runtime and the web part lives in ASP.NET Core.

When you call WebApplication dot CreateBuilder, three things are prepared. Configuration sources are lined up: the appsettings dot json file, the environment-specific file such as appsettings dot Development dot json, user secrets in development, environment variables, and command-line arguments, with later sources overriding earlier ones. Logging providers are added, such as the console. And a services list is created, already holding the framework's own registrations, including Kestrel as the server. Nothing has started. The key idea of the builder phase is: **you're writing lists. A list of service registrations, a list of settings sources. No requests can be handled, and no objects you registered exist yet.**

When you call builder dot Build, the services list is frozen and turned into the dependency injection container, which we'll meet in part five as the Supply Room. You get back a WebApplication object. In the development environment, the container is also built with two safety checks turned on, scope validation and validation on build. We'll see what those catch in part five.

Then you add middleware and endpoints to the app. This answers a question you asked in your first teach-back: why is the pipeline configured on the app, not on the builder? Because middleware often needs services that already exist, and services only exist after Build. And here's the mechanism, which almost nobody looks at. Calling app dot UseSomething does **not** run anything and does not create the middleware. Each Use call adds one entry to a list inside an object called ApplicationBuilder. Each entry is a Func of RequestDelegate and RequestDelegate: a function that, when later given "the next step", returns "a new step that does my work and then calls next". Mapping an endpoint, like app dot MapGet, doesn't add a middleware at all; it adds an entry to a separate list of endpoints, which routing will use.

Now you call app dot Run. This hands your main thread to the Stage Manager, which starts its hosted services. When GenericWebHostService starts, it does the most important piece of startup: it **builds the pipeline**. It calls a method named Build on the ApplicationBuilder, and that method is short enough to describe exactly. It starts with a final step that handles the case where nobody handled the request: that step sets the status code to 404, not found. Then it walks the list of middleware entries **backwards**, from the last one registered to the first. For each entry, it calls the entry's function, passing in the step built so far as "next", and keeps the step that comes back. When the loop ends, it's holding one single RequestDelegate: the first middleware, which knows the second, which knows the third, all the way down to the 404 step. Building it backwards is the only way to do it, because each step needs to be handed its "next" when it's created.

So the key idea is: **the whole pipeline becomes one RequestDelegate, built once at startup, by wrapping the steps from the last to the first.** A common misconception is that the framework walks the list of middleware on every request, like a loop that calls each one. Actually, the list is consumed once at startup, and what remains is a chain of objects that each call the next directly.

WebApplication also adds a few steps for you around your own. In development, a developer exception page goes first. If you've mapped any endpoints, routing is added before your middleware and endpoint execution after it, unless you placed them yourself. And if authentication or authorization services were registered, their middleware is added too. That's why a minimal app works without you writing UseRouting.

After the pipeline is built, GenericWebHostService hands it to the server, wrapped in an object we'll meet in part seven, and tells the server to start. Kestrel binds its sockets and begins accepting connections. Your main thread now sits inside Run until the app is told to shut down. When shutdown comes, for example from Control-C, the Stage Manager stops the hosted services in reverse order, Kestrel stops accepting new connections and gives in-flight requests time to finish, and then the container is disposed, which disposes every disposable service object that the container itself created.

Recap of part four. The Stage Manager, the Generic Host, owns configuration, logging, the container and the hosted services; the web part is one hosted service. The builder phase only writes lists. Build creates the container. Use calls add wrapping functions to a list; Map calls add endpoints. Run starts the host, which builds the pipeline once, backwards, into a single RequestDelegate that ends in a 404 step, and then starts the server.

## Part five: the services everyone asks for

Almost every class in ASP.NET Core receives its collaborators through its constructor. Take the HTTPS redirection middleware, which we'll use as our worked example in part seven. Its constructor takes four things: the next step in the pipeline, its options, the app's configuration, and a logger factory. Nobody in the repository writes "new HttpsRedirectionMiddleware" with those arguments. They come from four characters you'll meet in this part.

### The Supply Room: dependency injection

**The Supply Room** is the dependency injection container, which in .NET is called the service provider. It works in two phases, and keeping them apart clears up most of the confusion.

The first phase is **registration**, during the builder phase. A line like "services dot AddSingleton, of IClock and SystemClock" means "when anyone asks for an IClock, give them a SystemClock". That's a line on the Supply Room's list; nothing is created. Every area of ASP.NET Core has an extension method that adds its lines, like AddRouting, AddAuthentication or AddHttpsRedirection. Inside the repository, most of those lines use methods whose names start with TryAdd. The "Try" means "only add this if nobody has registered that interface yet". So an app that registers its own implementation first replaces the framework's default. That's one of the framework's main extension points.

The second phase is **resolution**, while the app runs. When the framework needs an object, it asks the Supply Room. The Supply Room looks at the class's constructor, finds or creates an object for each parameter using its list, and calls the constructor; and if those objects have constructor parameters of their own, it builds those first, all the way down. That's constructor injection.

Why bother? Because the class states what it needs, as an interface, a contract with no code, and doesn't decide where it comes from. In production the Supply Room hands it the real thing. In a test, the test hands it a fake that fulfills the same contract. That's the whole basis of the unit tests in part eleven.

Now **lifetimes**, which are where real bugs live. Every registration says how long its object lives. **Singleton** means one object, created the first time it's needed and shared by the whole app for its whole life. **Scoped** means one object per scope, and in ASP.NET Core a scope is one request: everything handling the same request shares one, and the next request gets a fresh one. **Transient** means a new object every time anyone asks.

A common misconception is that dependency injection creates a new object every time. Actually, that's only transient. Most of the framework's services are singletons, which has a big consequence: **a singleton is shared by every request being handled at the same moment, on many threads at once, so it must be safe for concurrent use.** That's why per-request information never lives inside framework singletons. It lives on the request object, which we'll meet in part six.

How does a request get its own scope? Through a small object called RequestServicesFeature. The first time anything on a request asks for request services, it creates a new scope from the Supply Room and registers that scope to be disposed when the response finishes. That's an ownership rule, and it's worth stating in the C terms you know. If a function in C calls malloc and then returns along an error path without calling free, the memory leaks: nobody holds the pointer any more, so nobody can release it. In .NET, "owning" an object means being responsible for calling its Dispose method, which releases things the garbage collector can't, like sockets, file handles and timers. **The rule in DI is: the container owns what the container created, and disposes it when its scope ends.** Scoped objects are disposed at the end of the request; singletons are disposed when the app shuts down. If you created an object yourself with new and handed it to the container, it's yours to dispose.

There's one classic lifetime bug, called a **captive dependency**. If a singleton's constructor asks for a scoped service, the singleton is created once and keeps that one scoped object forever. Now one request's object is being used by every request, and it might already be disposed. In the development environment, the scope validation switched on in part four catches the simplest form of this mistake and throws an error, rather than letting it slip through.

And here's the version you're most likely to meet in this repository. **A conventional middleware class is created once, when the pipeline is built, so it behaves like a singleton.** Its constructor runs one time, not per request. So if a middleware needs a scoped service, like a database context, it must not take it in its constructor. Instead it adds it as an extra parameter to its Invoke method, and the framework resolves that parameter from the current request's scope every time Invoke is called. There's also a second style of middleware, a class that implements an interface called IMiddleware, which the framework asks the Supply Room for on every request, so it can have any lifetime. You'll mostly see the conventional style in the repository.

### The Settings Board and the Options Packet

**The Settings Board** is configuration, the IConfiguration interface. It's a flattened dictionary of string keys to string values, merged from all the sources lined up in part four, with later sources overriding earlier ones. Nested JSON becomes keys joined with colons, so a setting nested under Kestrel, then Limits, then MaxRequestBodySize becomes one key with colons between the three names.

Raw strings aren't pleasant to work with, so most areas use **the Options Packet**, the options pattern. An area defines a plain class, like HttpsRedirectionOptions, with typed properties, such as the HTTPS port and the redirect status code. Registration code says how to fill it in: from a section of the Settings Board, from a lambda the app writes, or both. A class that needs it asks the Supply Room for IOptions of HttpsRedirectionOptions and reads its Value property. That Value is built the first time it's read, by running every registered configure step in order, and then it's reused. There are two siblings you'll see in the code: IOptionsSnapshot, which is rebuilt once per request so it can pick up configuration changes, and IOptionsMonitor, which is a singleton that tells you when settings change. The key idea is: **options are typed settings built from configuration plus code, and their names tell you how fresh they are.**

### The Scribe: logging

**The Scribe** is logging, the ILogger interface. A class asks for ILogger of its own type, or for a logger factory, and writes messages at levels from Trace up to Critical. Providers decide where messages go, like the console. You'll notice a strong convention in this repository: log messages are declared once, as partial methods marked with an attribute called LoggerMessage, usually in a file named something like HttpsLoggingExtensions. For example, the HTTPS redirection area declares a message with event id 1, level Debug, and the text "Redirecting to", followed by the address. A source generator, which is a compiler plug-in, writes the body of each method at build time. The reason is performance: it avoids building strings for messages whose level is switched off. When you add a log message in a contribution, follow that pattern rather than calling a general logging method with a string.

Recap of part five. The Supply Room works in two phases, registration then resolution, and TryAdd lets apps replace defaults. Lifetimes are singleton, scoped and transient; singletons are shared across concurrent requests; a request's scope is created on demand and disposed when the response ends; the container disposes only what it created. A captive dependency is a singleton holding a scoped object. Conventional middleware is built once, so scoped services go in Invoke's parameters. The Settings Board is flat string configuration; the Options Packet is typed settings; the Scribe logs through source-generated messages.

## Part six: the request object and its features

Now the object that every piece of the pipeline works on. Let's call it **the Job Ticket**. That's HttpContext, H-T-T-P context. There's exactly one Job Ticket per request, and it travels with the request from start to finish. Through it you reach the Request, with its method, path, query string, headers and body stream; the Response, with its status code, headers and body stream; the User, meaning who the request is from once authentication has run; RequestServices, the request's own scope in the Supply Room; RequestAborted, a cancellation token that fires if the client disconnects; and Items, a small dictionary any piece of the pipeline can use to leave notes for later pieces.

Here's the part almost no one knows, and it explains a lot of the code you'll read. **The Job Ticket doesn't store most of that data itself.** Underneath it is a collection of **features**, and every property on the Job Ticket is a thin front that reads from or writes to a feature. Let's call that collection **the Feature Drawers**. Each drawer is labeled with an interface type and holds an object implementing that interface. There's a drawer labeled IHttpRequestFeature that holds the raw method, path and headers. There's one for the response, one for the response body, one for the TLS connection details, one for the request's service scope, and many more. When your code reads context dot Request dot Method, the request object opens the IHttpRequestFeature drawer and reads its Method property. That's it.

Why add this indirection? Because ASP.NET Core supports several servers, and each one has completely different internals. Kestrel, HTTP.sys on Windows, IIS, and the in-memory TestServer that tests use each fill the drawers with their own objects, and everything above the drawers works unchanged. The key idea is: **features are the contract between a server and the rest of the framework. The server fills the drawers; HttpContext is a convenient front over them; and middleware can add or replace drawers to change behavior for everything after it.**

That last clause matters. Response compression, for example, works by replacing the response-body drawer with its own object that compresses whatever is written into it, and then calling the next step. Code later in the pipeline writes to "the response body" as usual and has no idea it's being compressed. A middleware that wants to offer something new, like information about the matched endpoint, puts it in a new drawer for later pieces to find.

And here's a nice fact about Kestrel specifically. Kestrel's internal per-connection object, a class called HttpProtocol, **is itself the feature collection**. It implements the interface for the drawers directly, along with many of the feature interfaces. So when HttpContext reads the method from the request drawer, on Kestrel it's very often reading a field on Kestrel's own object, with no copying in between. That's one reason the abstraction costs so little.

There's a consequence of this design that's worth stating as a rule, because getting it wrong produces bugs that are very hard to find. **You must not hold on to the Job Ticket after the request finishes.** The framework reuses these objects: when a request ends, the context and Kestrel's per-request state are reset and pooled for a later request. If some code stashes the HttpContext in a field and reads it later, from a background task, say, it may be reading a different request's data, or a half-reset object. The Job Ticket is valid only while the request is in progress. If you need something from it later, copy the value out while the request is still running.

A second rule: **HttpContext is not thread-safe.** One request's code normally runs as a single logical flow, one step after another, even if it hops between threads at awaits. If you start two pieces of work in parallel that both touch the same HttpContext, nothing protects you.

Recap of part six. The Job Ticket, HttpContext, is the one object per request that every piece receives. Most of its properties are fronts over the Feature Drawers, a collection of objects keyed by interface type that the server fills in. Features let different servers plug in and let middleware change behavior by swapping drawers. Kestrel's HttpProtocol is itself the feature collection. Don't keep the Job Ticket after the request ends, because it's pooled and reused, and don't use it from two threads at once.

## Part seven: one request's journey, step by step

This is the main event. Let's follow one request through the whole framework and say, at each step, who hands what to whom.

Here's the app. It's a minimal API app. In the builder phase it registers authentication and authorization services and a service of its own called the to-do store, as a singleton. After Build, it calls app dot UseHttpsRedirection. Then it maps one endpoint: a GET request to the path slash todos slash, followed by a route parameter named id in curly braces. The handler is a lambda with two parameters, an int called id and the to-do store, and it returns the store's to-do item for that id. The endpoint also calls RequireAuthorization, which means only signed-in users may call it.

Now the cast for this part, all in one place. **The Listener** is Kestrel, the web server: it owns the sockets and speaks HTTP. **The Hand-off Desk** is a class called HostingApplication: it's the single point where the server hands a request to the framework and gets it back. **The Job Ticket** is HttpContext, sitting on top of **the Feature Drawers**. **The Assembly Line** is the pipeline, the single RequestDelegate built at startup. **The Doorman** is the HTTPS redirection middleware. **The Sorter** is the routing middleware, a class called EndpointRoutingMiddleware. **The ID Checker** is the authentication middleware and **the Guard** is the authorization middleware. **The Runner** is a class called EndpointMiddleware, which runs whatever endpoint the Sorter chose. And **the Adapter** is a class called RequestDelegateFactory, which, at startup, turned your lambda into a RequestDelegate.

Step one: the connection. A client opens a TCP connection to port 80. Kestrel's transport layer, which by default uses ordinary operating-system sockets, accepts it. Kestrel creates a connection object and decides which version of HTTP it's speaking. This is plain HTTP/1.1, so the connection is handled by an object called Http1Connection, which is one kind of HttpProtocol, the class that is also the Feature Drawers.

Step two: parsing. Bytes arrive. Kestrel's parser reads the request line, "GET slash todos slash 5, HTTP/1.1", and the headers, and stores them in fields on its HttpProtocol object, which is the same object that answers for the request drawer. Note what doesn't happen: the request body is not read yet. Kestrel reads a body only when, and as fast as, application code asks for it. This is how it protects memory.

Step three: the hand-off. Kestrel calls the Hand-off Desk's CreateContext method, passing itself as the feature collection. The Hand-off Desk creates the Job Ticket, a DefaultHttpContext over those drawers, or, if this connection already has one from a previous request, it re-initializes that pooled one. It also starts the request's diagnostics: a timestamp, a tracing activity for distributed tracing, metrics, and the "request starting" log line. Then Kestrel calls the Hand-off Desk's ProcessRequestAsync, which does exactly one thing: it invokes the Assembly Line, the pipeline delegate, with the Job Ticket. From here on, until that call returns, the request is in your app's hands.

Step four: the Doorman. The first step on the line, in this app, is the HTTPS redirection middleware. Its Invoke method is short enough to describe in full. First: if the request's IsHttps property is true, call next and return; nothing to do. Second: work out which port HTTPS is on. It checks, in order, the options, then the HTTPS underscore PORT configuration setting, then the addresses the server is listening on. If it can't find one, it logs a warning once and calls next, letting the request through unredirected. Third: otherwise, build the same address with "https" in front and the HTTPS port; set the response status code to 307, temporary redirect; set the Location header to that address; log "Redirecting to" and the address; and return a completed Task **without calling next**.

That last detail is the key idea of middleware. **A middleware that doesn't call next is called short-circuiting: the chain ends there, and the calls unwind back to Kestrel.** Our request was plain HTTP, so the Doorman short-circuits. The Sorter, the Guard and your lambda never run. The pipeline call returns, Kestrel writes the 307 response with its Location header, and the client, seeing the redirect, opens a new connection on port 443 and sends the same request again. Let's follow that second request.

Step five: the second request. This time the connection uses TLS. Kestrel performs the TLS handshake, decrypts the bytes, and very likely negotiates HTTP/2, in which case each request is a stream inside the connection, handled by its own HttpProtocol object. Everything after that looks the same as before: parse, Hand-off Desk, new Job Ticket, Assembly Line. This time the Doorman sees IsHttps is true, and calls next.

Step six: the Sorter. Next on the line is the routing middleware, added for you by WebApplication. At startup, it collected every endpoint from every source, your MapGet calls plus anything else like controllers, and built an efficient matcher: a state machine that walks the path one segment at a time, followed by checks on the HTTP method and other constraints. Now it runs the matcher. The path slash todos slash 5 with method GET matches your endpoint, and the route value id is captured as the string "5". The Sorter puts the chosen endpoint into the endpoint drawer, and the route values into the route-values drawer. Then it calls next. Notice what the Sorter does not do: **it doesn't run the endpoint. It only chooses it.** That split is deliberate. It lets every middleware between choosing and running read which endpoint was chosen, and that endpoint's metadata, and act on it.

An endpoint, by the way, is exactly three things: a RequestDelegate that handles the request, a display name for logs, and a bag of **metadata**, objects attached to it that describe it. Your RequireAuthorization call added an authorization metadata object to that bag.

Step seven: the ID Checker and the Guard. The authentication middleware runs the app's default authentication scheme, which, for a cookie scheme, reads and decrypts the sign-in cookie, and sets the Job Ticket's User property to the identity it found, or to an anonymous one. It doesn't reject anyone. Then the authorization middleware, the Guard, reads the chosen endpoint's metadata, finds the authorization requirement, and evaluates it against the User. If the user is anonymous, it short-circuits with a challenge, which for cookies means a redirect to the login page, or for an API typically a 401. If the user is allowed, it calls next. The key idea is: **authentication answers "who are you", authorization answers "are you allowed", and authorization can only work after routing, because it needs to know which endpoint was chosen.**

Here's a nice safety net you'll find in the Runner's code. If an endpoint carries authorization metadata, but the Guard never ran, for example because someone placed UseAuthorization in the wrong spot, the Runner throws an error that says so, instead of silently running an endpoint that was supposed to be protected. It knows the Guard ran because the Guard leaves a note in the Job Ticket's Items dictionary. That's a good example of how the pieces communicate: through the Job Ticket, never through each other directly.

Step eight: the Runner and the Adapter. The endpoint middleware reads the chosen endpoint from the drawer and invokes its RequestDelegate. For a minimal API, that RequestDelegate was generated at startup by the Adapter. When you called MapGet with a lambda, RequestDelegateFactory looked at the lambda's parameters and return type, and built a RequestDelegate that does the plumbing for you. The parameter named id is an int, and there's a route value called id, so the generated code reads the route value "5" and parses it into the integer 5. If parsing failed, it would respond with 400, bad request, and your lambda would never run. The to-do store parameter is a registered service, so the generated code asks the request's scope in the Supply Room for it. Then it calls your lambda. Your lambda returns a to-do item object. The generated code sees that it's an ordinary object, not a string and not an IResult, so it serializes it to JSON, sets the content type to application slash json, and writes it to the response body. If your lambda had returned a string, it would write plain text instead. If it had returned an IResult, such as Results dot NotFound, it would call that result's ExecuteAsync method, letting the result object write the response itself.

There's also a second way the Adapter's work can happen: a source generator called the Request Delegate Generator, which writes the same plumbing as C# code at compile time instead of building it at startup. It's used when apps are compiled ahead of time to native code, where building code at run time isn't allowed. Both live in the Http dot Extensions folder.

Step nine: writing and unwinding. When your code first writes to the response body, the response **starts**: the status code and headers are sent first, then the body bytes. From that moment, the status code and headers can no longer be changed, because they've already left the machine. The Job Ticket's Response dot HasStarted property tells you whether that point has passed, and middleware that wants to change headers must do it before then, or register a callback with Response dot OnStarting. Now your lambda's Task completes, and the calls unwind: back out of the Adapter's delegate, out of the Runner, the Guard, the ID Checker, the Sorter, and the Doorman. Each middleware, as the call returns to it, has a chance to do work on the way out, which is how timing and logging middleware measure the whole request.

Step ten: finishing and cleanup. The pipeline call returns to Kestrel. Kestrel finishes the response: if nothing was written, it sends the headers now; it flushes any buffered data; it marks the end of the response. Then Kestrel calls the Hand-off Desk's DisposeContext. That ends the diagnostics, writing the "request finished" log line with the status code and duration. It disposes the request's scope, which disposes every scoped and transient disposable object the scope created. And it resets the Job Ticket so it can be reused. For an HTTP/1.1 connection, Kestrel then loops around to read the next request on the same connection.

What if your lambda throws an exception? The exception travels back up through the unwinding calls. Any middleware with a try and catch around its call to next can handle it, which is exactly what the developer exception page and the exception handler middleware do. If nothing catches it, Kestrel catches it at the very top, logs it as an unhandled application error, and responds with 500, internal server error, if the response hasn't started yet. If it has started, Kestrel can only abort the connection, since the status line already went out.

Recap of part seven. The Listener accepts and parses; the Hand-off Desk creates the Job Ticket and invokes the Assembly Line. Each middleware either calls next or short-circuits, as the Doorman did with a 307. The Sorter chooses an endpoint and stores it in a drawer but doesn't run it. The ID Checker sets the user; the Guard reads the endpoint's metadata and allows or challenges. The Runner invokes the endpoint's delegate, which the Adapter generated from your lambda to bind parameters and write the result. Headers can't change once the response has started. The calls unwind, and DisposeContext disposes the request scope and resets the Job Ticket.

## Part eight: async code, threads and cancellation

Every method on the request path returns a Task, and you'll see the keyword await on most lines. Let's make the mechanism exact, because a fuzzy model of it causes real bugs, and reviewers in this repository care about it a great deal.

Start with the problem. A web server spends most of each request waiting: for the client's bytes to arrive, for a database, for another service. The simplest design gives every request its own thread and lets that thread block, sitting idle, while it waits. That works until you have ten thousand slow requests and ten thousand threads, each holding its own stack memory and costing the operating system scheduling work. The alternative is to wait without holding a thread.

Here's the honest comparison with C. In C, a blocking read call parks your thread inside the kernel until data arrives. The non-blocking alternative is an event loop: you ask the operating system to tell you when a socket is ready, using something like epoll on Linux, and you register a callback that continues the work. Event loops are efficient, but writing them by hand is miserable, because every function that waits has to be chopped into "before the wait" and "the callback after the wait", with state carried between them by hand.

C# async and await is the compiler doing that chopping for you. When you mark a method async, the compiler rewrites it into a small state machine object. Each await is a point where the method can be split. At an await, if the awaited Task is already finished, the method simply carries on, no pause at all. If it isn't, the method registers "the rest of me" as a continuation on that Task, and returns to its caller immediately, handing back a Task of its own that represents "the rest of me, not done yet". The thread is now free, and goes back to the .NET thread pool, a shared set of worker threads, to run other requests. When the awaited work finishes, for example because the operating system reported that the socket has data, a thread-pool thread picks up the continuation and runs the method from where it left off. Kestrel itself is built this way all the way down, using a library called System dot IO dot Pipelines for its buffers.

So the key idea is: **await means "pause this method here without blocking a thread". It doesn't create a thread, and it doesn't run anything in parallel.** A common misconception is that async means "runs on a background thread". Actually, an async method runs on the calling thread until its first await that has to wait, and the rest may resume on a different thread-pool thread. For one request, it's still one logical sequence of steps, just not pinned to one thread.

Two consequences follow, and both show up in code review. First, **never block on a Task.** Calling a Task's Result property or its Wait method makes the current thread sit idle until the work finishes. Do that on many requests at once and the thread pool runs out of free threads; requests then queue up waiting for a thread, even though the CPU is idle. This is called thread-pool starvation, and it's one of the most common causes of mysterious slowdowns in ASP.NET Core apps. The rule is: async all the way up. If you call something that returns a Task, your method becomes async too, and you await it.

Second, a note on a type you'll see in performance-sensitive code in this repository: **ValueTask**. It's a variant of Task that avoids allocating an object when the result is usually available immediately, which is common in Kestrel's read and write paths. It comes with rules: await it once, and don't store it to await later. When reading code, treat it like a Task.

Now **cancellation**. Every request has a CancellationToken, available as the Job Ticket's RequestAborted property, which fires when the client disconnects or the server aborts the request. Async methods throughout the framework take a token as their last parameter, and you pass it along. Here's what a token does not do, because it's easy to assume more. **A cancellation token doesn't stop or kill anything by itself.** It's a flag plus a list of callbacks. Code has to check it, or pass it to an operation that checks it, and then stop on its own. If your code ignores the token, the work keeps running to completion even though the client left. Cancellation in .NET is cooperative.

And remember the rule from part six: one request's code is one logical sequence, so HttpContext doesn't need locks for normal use. That stops being true the moment your code starts two pieces of work at the same time and lets both touch the Job Ticket, so don't.

Recap of part eight. Async and await let a method wait without holding a thread; the compiler turns the method into a state machine that resumes on a thread-pool thread when the awaited work completes. Await doesn't create threads or parallelism. Never block on a Task with Result or Wait; that leads to thread-pool starvation. ValueTask is a cheaper Task with stricter rules. Cancellation tokens are cooperative flags; RequestAborted fires when the client goes away, but code must check it.

## Part nine: a tour of the big feature areas

Everything so far is the core: hosting, servers, the HTTP abstractions, routing and middleware. Now the large areas that sit on top. The point of this part is for you to recognize each one and know how it connects to the core, not to learn them all. The connecting idea, stated once: **almost every area plugs in the same two ways: an Add method that registers services in the Supply Room, and either a Use method that adds middleware or a Map method that adds endpoints.**

**MVC**, in the src slash Mvc folder, is the older and larger programming model, with controllers, which are classes whose public methods, called actions, handle requests. From routing's point of view, each controller action is just an endpoint, discovered at startup by scanning your assemblies for controllers. The difference is what that endpoint's RequestDelegate does. It hands the request to a character we'll call **the Invoker**, a class named ControllerActionInvoker. The Invoker runs MVC's own inner pipeline, called **filters**: authorization filters, resource filters, then model binding, which builds the action's parameters from the route, query string, headers and body, then validation, then action filters around the action call itself, then exception filters, then result filters around writing the result. The controller object itself is created fresh for every request. So MVC is a second, richer pipeline that runs inside one endpoint of the first. The folder's own AGENTS file gives its testing conventions: unit tests next to each project, and functional tests that host whole sample sites from a folder called WebSites.

**Razor Pages** is a page-focused model built on the same MVC machinery, where each page is a Razor file with an optional class behind it. **Razor** itself is the syntax that mixes HTML and C#. The runtime pieces that execute compiled Razor views live here; the Razor compiler, which turns Razor files into C#, lives in a separate repository, dotnet slash razor.

**Blazor**, in src slash Components, is the largest and most different area, so here is the bound up front: **Blazor does not use the request pipeline for its interactivity.** It's built around components that produce a render tree, a description of the user interface. A renderer compares each new render tree with the previous one and sends only the differences to the browser. Where that runs depends on the render mode. With static server rendering, components run once per request, through a normal endpoint, and produce HTML. With interactive server rendering, components stay alive on the server in what's called a circuit, and user events and interface updates travel over a persistent SignalR connection. With interactive WebAssembly, the .NET runtime itself is downloaded into the browser and the components run there. The folder has its own ARCHITECTURE file, which is the place to start if you ever work there, plus a lot of TypeScript, which is why the repository needs Node.js to build.

**SignalR**, in src slash SignalR, provides real-time, two-way messaging. The server defines a hub, a class whose methods clients can call, and the server can call methods on clients, individually, in groups, or all at once. Underneath, it negotiates the best transport the client supports, WebSockets first, then server-sent events, then long polling, and encodes messages as JSON or MessagePack. There are clients in .NET, TypeScript and Java in the same folder. A SignalR hub is mapped as endpoints like anything else, and from then on, the long-lived connection is handled by SignalR's own layers. As of today's commit, it also has an ARCHITECTURE file; it was added on the very commit these facts were checked against.

**Security** covers authentication and authorization, which you met as the ID Checker and the Guard. Authentication is organized around **schemes**, named handlers like cookies or JWT bearer tokens, each with three jobs: authenticate, meaning work out who the request is from; challenge, meaning respond when someone needs to sign in; and forbid, meaning respond when someone is signed in but not allowed. Authorization is organized around **policies** made of requirements. **Identity**, in its own folder, is a full user-account system on top of that: users, passwords, two-factor, and stores, usually backed by Entity Framework. **Data Protection** is the encryption service that protects cookies and tokens; it manages and rotates its own keys, and many security features depend on it. **Antiforgery** protects form posts against cross-site request forgery.

**Middleware**, in src slash Middleware, is the collection of ready-made pipeline pieces: static files, response compression, response caching and the newer output caching, rate limiting, CORS, URL rewriting, sessions, health checks, WebSockets, request decompression, HTTP logging, forwarded headers, and HTTPS redirection, which we walked through. These are the smallest, most self-contained projects in the repository, each one usually a middleware class, an options class, extension methods for Add and Use, and a test project. That makes them the friendliest place for a first contribution.

A few smaller areas round it out. **OpenAPI** generates a machine-readable description of your API. **gRPC**: the main gRPC library for .NET lives in a separate repository, grpc slash grpc-dotnet; this repository holds JSON transcoding, which lets gRPC services also be called as JSON over HTTP, and interop tests. The **HttpClientFactory** folder now holds only the integration with Polly, a third-party resilience library, shipped as a separate package; the factory itself lives in dotnet slash runtime. **ProjectTemplates** holds the templates behind dotnet new for web projects. **Servers** also contains the Windows-only HTTP.sys server and the IIS integration, which includes a native module written in C plus plus. That's the reason the repository has a copy of Google's C plus plus test framework as a git submodule.

Recap of part nine. Every area plugs in with Add for services and Use or Map for the pipeline. MVC runs its own filter pipeline inside one endpoint, through the Invoker. Razor Pages builds on MVC. Blazor renders components and sends differences, and its interactivity doesn't use the request pipeline. SignalR keeps two-way connections over the best available transport. Security is schemes for authentication and policies for authorization. The Middleware folder's small, self-contained projects are the friendliest entry point.

## Part ten: a walk through the repository, and how to build it

Now let's walk the repository as you'll meet it after cloning, and then the build, because this repository's build is unlike anything in YARP or dotnet slash iot, and it's where first-time contributors lose the most time.

At the top level there are four things that matter. The src folder holds all the product code, organized by area. The eng folder, short for engineering, holds the build system. The docs folder holds contributor documentation: how to build, how API review works, how servicing works, area owners, and more. And there's a dot github folder with the issue and pull request templates, the code owners file, and a file of instructions written for AI coding assistants, called copilot-instructions. That last one is worth reading even though it's aimed at AI tools, because it's the most compact statement of the team's current conventions: file-scoped namespaces, "is null" instead of double-equals, minimal diffs that don't touch unrelated lines, no "Arrange", "Act" or "Assert" comments in tests, xUnit for tests, Moq for mocking, and a strict rule about proving a fix, which we'll come to in part eleven. Several areas also have their own AGENTS file with area-specific rules, and Blazor and SignalR have ARCHITECTURE files.

Inside src, each area folder follows the same shape. Take src slash Middleware slash HttpsPolicy. It has a src folder with the product code: the middleware, its options, its extension methods, its log messages, the project file, and two text files called PublicAPI dot Shipped and PublicAPI dot Unshipped, which we'll get to. It has a test folder with the test project, Microsoft dot AspNetCore dot HttpsPolicy dot Tests. Bigger areas also have a samples folder, a testassets folder for apps that tests run against, and, at the area's top, three helper scripts: a build script, a startvs script that opens Visual Studio on just this area, and startvscode for VS Code. There's also a solution filter file, ending in dot slnf, that lists just this area's projects. That's needed because the whole repository's solution, AspNetCore dot slnx, contains hundreds of projects, more than an editor handles comfortably. A solution filter is a view onto a subset of it.

Two things in project files will look strange. First, projects refer to each other with Reference elements, not the usual ProjectReference or PackageReference. The repository's build system decides, for each Reference, whether it should become a reference to another project in the repo or to a package of a specific version, based on servicing rules. The docs are explicit: use Reference in product projects, never PackageReference, and ProjectReference only in tests. Second, the PublicAPI files. **Every public type and member in a shipping project is listed, one per line, in those two text files.** Shipped holds what was in the last major release and is only edited by the build team. Unshipped holds what's been added or removed since. An analyzer, which is a compiler plug-in that reports warnings and errors, compares the code with those files on every build. If you add a public method and forget the Unshipped file, the build fails with an error code starting RS0016. The point is that nobody can change the framework's public surface by accident. That ties directly into the API review process in part twelve.

The eng folder holds the build machinery. The main files are Versions dot props, which lists dependency versions; Version dot Details dot xml, which records exactly which build of dotnet slash runtime and other repositories this repository consumes; and Dependencies dot props. A bot called Maestro opens pull requests regularly, usually titled "Update dependencies from dotnet slash runtime", that bump those versions as new builds of the runtime come out. You'll see those pull requests constantly; they're machine traffic, not something to review. The eng slash common folder is shared build infrastructure from a repository called Arcade, which all dotnet repositories use, and it's synced automatically, so it's never edited by hand here.

Now the build. Here's the order, from the repository's build guide. Step one: fork the repository and clone your fork with the dash dash recursive flag, because the repository uses git submodules: MessagePack for SignalR, and the C plus plus test framework for the IIS module. Step two: run the restore script at the root, restore dot sh on your Mac. It downloads the exact preview SDK named in global dot json into a hidden folder inside the clone, called dot dotnet, and restores dependencies. That matters because the SDK that the repository needs is newer than any you'd have installed: today, a .NET 11 release-candidate SDK. Step three: run "source activate dot sh", which points your terminal's dotnet command at that in-repo SDK. Forgetting this step is the single most common cause of confusing build errors. Step four: go into the area you care about and build only that area, with its own build script, or with dotnet build and dotnet test on a single project file. The guide says plainly that you'll rarely need to build the whole repository, and recommends against running the top-level build. Areas with JavaScript, like Blazor and SignalR, also need Node.js installed. Build outputs from every project go into one shared folder at the root, called artifacts.

Here's what has and hasn't been checked. These steps come from the repository's documentation at today's commit. They have not been tried on your Mac yet. From your YARP setup notes, your Linux desktop can't run the .NET 11 SDK, so the same applies here: use the Mac or a GitHub Codespace. A Codespace has the advantage that the repository's own setup runs the restore for you.

Recap of part ten. Product code is in src, by area; each area has src, test, often samples and testassets, its own build script and a solution filter. Product projects use Reference elements, resolved by the build. PublicAPI Shipped and Unshipped files list the public surface, and an analyzer fails the build if code and files disagree. The eng folder holds versions and the shared Arcade infrastructure, and the Maestro bot keeps dependencies flowing from dotnet slash runtime. To build: clone recursively, run restore, source activate, then build and test one area or one project.

## Part eleven: testing in this repository

Testing here works in layers, and the repository's names tell you which layer you're in.

**Unit tests** live in a project named after the product assembly with dot Tests on the end, or dot Test in some older areas like MVC; the guidance is to keep whatever suffix the area already uses, because the build uses those names to find test projects. **Functional tests**, in projects ending in dot FunctionalTests, start a real app with a real or test server and make HTTP calls to it. **End-to-end tests**, ending in E2ETests, drive a real browser through Selenium or Playwright, mostly for Blazor and the project templates. Tests use xUnit, version 3. A method marked with the Fact attribute is one test. A method marked with Theory runs once per data row, and the rows are given with InlineData attributes.

Let's walk one real test, object by object, the way your earlier lectures did, because the object graph is the thing to hold on to. It's in the HTTPS redirection test project, a theory named SetOptions underscore SetStatusCodeHttpsPort. It has five data rows. Each row gives a status code, an HTTPS port, and the redirect address the test expects. For example: 302 with port 5001 should redirect to https colon slash slash localhost colon 5001; and 301 with port 443 should redirect to https colon slash slash localhost with no port at all, because 443 is the default HTTPS port. That last row exists to test the Doorman's "if the port isn't 443" branch from part seven.

First, what's real and what's replaced. **Real:** the Generic Host, the pipeline builder, the HTTPS redirection middleware itself, the options system, and a tiny terminal step at the end of the pipeline that writes "Hello world". **Replaced:** two things. The server: instead of Kestrel, the test calls UseTestServer, which plugs in **TestServer**, an in-memory server. TestServer implements the same server interface as Kestrel and fills the same Feature Drawers, but there are no sockets: its HttpClient hands requests straight to the pipeline in memory. That's the features design from part six paying off; nothing above the drawers can tell the difference. And the logger factory: the test registers a TestLoggerFactory that writes into a **TestSink**, an object that just records every log message in a list, so the test can inspect them afterwards.

Now the three moves. **Arrange:** build the host. Register the test logger factory as a singleton. Configure HttpsRedirectionOptions with this row's status code and port. In the pipeline, call UseHttpsRedirection, then the terminal step. Start the host. **Act:** get an HttpClient from the TestServer and send a GET request. The TestServer's default address is plain http colon slash slash localhost, so the request is not HTTPS and the Doorman should redirect. **Assert:** the response's status code equals this row's code; the Location header equals the expected address; and the sink holds exactly one log message, the "Redirecting to" message.

Notice two things about this test. First, there's no mocking library in it. The replacements are hand-written test doubles that ship with the repository's testing helpers. "Test double" is the general word for any stand-in object in a test. A **fake** is a working, simplified implementation, like TestServer. A **mock**, created with Moq, is a stand-in you script per test: "when this method is called, return this", and afterwards, "verify this method was called". You used both in your dotnet slash iot work: the GPIO driver was a Moq mock. In this repository you'll see both styles, and the rule is to copy what nearby tests in the same project do.

Second, this is a test of the middleware through a real host. The other common style in this repository creates a DefaultHttpContext directly, sets the request's scheme and host on it, constructs the middleware with a lambda as its next step, calls Invoke, and then checks the response on the context, all with no host and no server. That's faster and narrower. Both are unit tests in the sense that matters: they run in memory, quickly, without a network.

Now the rule that you'll be held to, from the repository's own instructions. **Before claiming a fix works, show that the test fails for the expected reason without the fix, and passes with it.** That's red, then green, the same discipline you used for dotnet slash iot pull request 2611. The instructions add a subtlety about theories: a red result only proves at least one row failed, so check every row's outcome, and make sure each row actually exercises the code path it claims to.

Finally, what happens to tests in continuous integration. Pull requests run on Azure Pipelines, in a public pipeline. The tests themselves are shipped to **Helix**, Microsoft's distributed test service, which runs them on a matrix of machines: several versions of Windows, Linux and macOS. Because so many tests run on so many machines, some are flaky, failing occasionally for reasons unrelated to the change. The team handles that with **quarantine**: a flaky test gets a QuarantinedTest attribute pointing at a tracking issue, and quarantined tests run in a separate pipeline so they don't block pull requests. A common misconception is that a red check on your pull request always means your change broke something. Actually, in a repository this size, it's often a known flaky test or an infrastructure hiccup. The right move is to open the failure, read which test failed and why, and say what you found in a comment, rather than either panicking or ignoring it.

Recap of part eleven. Test projects are named dot Tests, dot FunctionalTests or E2ETests, and the names matter to the build. Facts are single tests; theories run once per InlineData row. In the walked test, the host, pipeline, middleware and options are real; the server is replaced by the in-memory TestServer and the logger by a recording sink. Fakes are working stand-ins; mocks are scripted ones. Prove a fix red then green, row by row. CI runs tests on Helix across many machines, and flaky tests are quarantined.

## Part twelve: the contribution process, the common misconceptions, and the final recap

### How a change gets into ASP.NET Core

You've now opened pull requests to two .NET repositories, so let's focus on what's different here. ASP.NET Core is one of the busiest repositories in the .NET organization, with a small team triaging a large flow of issues, and its process is built to protect that team's time.

Start with choosing an issue. Every issue gets an **area label**, like area-middleware, area-networking, area-minimal, area-mvc or area-blazor, and the docs folder lists who owns each area. The team marks issues it would welcome community pull requests for with the **help wanted** label, and the subset suitable for newcomers with **good first issue**. The contributing guide is direct about why: over the years, contributors spent effort on pull requests in areas the team didn't plan to change, and those had to be closed. So the rule is: pick a help-wanted issue, or first get agreement from the team on the issue. For anything bigger than a small fix, the guide asks you to describe your approach, and wait for a positive response, before investing much effort, and for real design changes to file a **design proposal** issue first. That matches the way you already work: build and understand privately, then comment, then open the pull request.

Next, the **public API rule**, which is the biggest difference from YARP and dotnet slash iot. Any new or changed public or protected type, member, signature or default counts as a public API change. You must add it to the PublicAPI Unshipped file, or the build fails, as we saw in part ten. But the Unshipped file only tracks the change; **it doesn't grant approval.** Approval comes from **API review**: a separate API proposal issue, written in what's called reference-assembly format, meaning just the signatures, with no method bodies, plus a short explanation that someone outside the area can follow. When it's ready, a team member, the issue owner, who acts as the champion for a community proposal, labels it api-ready-for-review, and it's discussed in a weekly API review meeting. If approved, it gets the api-approved label. The implementation may be reviewed and even merged before that, but nothing ships in a final release without approval matching the final shape. The practical lesson for a first contribution: **prefer issues that change behavior without adding public API.** Those avoid the whole review track. A related rule: in shipping code, you mustn't reach into another framework assembly's internal members with tricks like InternalsVisibleTo; if two assemblies need to share something, that's a design question for the team.

Then the pull request itself. The template asks you to confirm you've read the contributing guide and code of conduct, included tests where applicable, included documentation comments, and that there's an open issue; then a summary under 80 characters, a description, and a "Fixes" line with the issue number in that exact format, "Fixes", space, hash, number. The **Contributor License Agreement** is signed once for every .NET Foundation project, and you already signed it for dotnet slash iot, so the CLA bot should recognize your account. Reviews can take a while. A pull request with no activity for two weeks is marked stale, and closed four days after that, so if a reviewer asks for changes, respond, even if just to say when you'll get to it. Merges are squashed into a single commit.

Finally, **branches and releases.** Your pull request targets main. On today's commit, main is already building .NET 12; .NET 11 is on the release slash 11.0 branch, in its release-candidate phase, and is due to ship in November, as each new major version has. Older versions live on release branches like release slash 10.0 and release slash 9.0. A fix doesn't automatically go into those. Patches to a shipped version have a high bar, decided by a cross-team group called Shiproom: the fix must affect many users, have no reasonable workaround, and **never change public API**, because apps must keep working with every patch of their version. For external contributors, a team member handles that process. So: target main, and if you think a fix deserves a patch, say so in the pull request and let the team decide.

### The common misconceptions, one more time

Here they are, each as the wrong version, then the correction.

Misconception: ASP.NET Core reaches your app as a set of NuGet packages. Actually, most of it is the shared framework, Microsoft dot AspNetCore dot App, installed once per machine with the runtime and selected by the Web SDK.

Misconception: the using directive gives your code access to a library. Actually, access comes from the reference in the project; using only shortens names.

Misconception: an extension method like UseHttpsRedirection is a method on the app object. Actually, it's a static function in a separate class, with dot-call syntax and no special access.

Misconception: the framework loops over the list of middleware on every request. Actually, the list is consumed once at startup, building one RequestDelegate from the last step to the first; each request just calls that delegate.

Misconception: middleware are separate stages or threads that requests queue through. Actually, they're nested method calls on one request's flow; each one runs code on the way in and on the way out.

Misconception: the routing middleware runs your endpoint. Actually, it only chooses the endpoint and stores it on the Job Ticket; the endpoint middleware runs it later, and in between, middleware like authorization reads the choice.

Misconception: dependency injection creates a fresh object every time. Actually, only transient services do; singletons are shared by all concurrent requests and must be thread-safe, and scoped services live for one request.

Misconception: a middleware class is created per request. Actually, a conventional middleware is created once, so scoped services must be taken as parameters of Invoke, not the constructor.

Misconception: it's fine to keep a reference to HttpContext for later. Actually, it's pooled and reset after the request; copy what you need out of it during the request.

Misconception: await starts a new thread. Actually, await pauses the method without blocking any thread, and the rest resumes later, often on a different thread-pool thread.

Misconception: a cancellation token stops work. Actually, it's a cooperative flag; code has to check it and stop itself.

Misconception: a bug in dependency injection, configuration or logging gets fixed in this repository. Actually, those Microsoft dot Extensions libraries live in dotnet slash runtime.

Misconception: adding a small public method is a small change. Actually, any public API change needs the PublicAPI baseline entry and an approved API review, so it's a much bigger process than a behavior fix.

Misconception: a red check on a pull request always means your change broke something. Actually, it's often a known flaky test or an infrastructure problem; read the failure, then say what you found.

### The final recap

Here are the ten ideas to take away. They're also what to say back in a teach-back.

One. ASP.NET Core is a framework: when you call Run, it takes over the main loop and calls your code for each request. Its repository holds the servers, hosting, HTTP abstractions, routing, middleware, security and the programming models; the Microsoft dot Extensions building blocks live in dotnet slash runtime.

Two. Most of ASP.NET Core arrives as the shared framework, installed once per machine. Assemblies are compiled IL files, namespaces are naming prefixes, packages are delivery zips, and abstractions assemblies hold contracts while the implementation lives next door.

Three. Extension methods are static functions with dot-call syntax. Lambdas create delegates that can capture variables. RequestDelegate, a function from HttpContext to Task, is the most important type in the framework.

Four. Startup writes lists in the builder phase, creates the container in Build, and, when Run starts the host, builds the whole pipeline once, backwards, into a single RequestDelegate that ends in a 404 step.

Five. The Supply Room resolves constructor parameters. Singletons are shared by all requests, scoped services live for one request and are disposed with it, and the container disposes only what it created. Conventional middleware is built once.

Six. The Job Ticket, HttpContext, is a front over the Feature Drawers, which the server fills. Features let Kestrel, IIS and TestServer plug in interchangeably, and let middleware change behavior by swapping drawers. The Job Ticket is pooled, so don't keep it.

Seven. A request travels: the Listener parses, the Hand-off Desk creates the Job Ticket and calls the pipeline, each middleware calls next or short-circuits, the Sorter chooses an endpoint, the Guard checks it, the Runner runs it, the Adapter binds parameters and writes the result, and cleanup disposes the request's scope.

Eight. Await pauses a method without holding a thread; never block on a Task; cancellation is cooperative.

Nine. In tests, know what's real and what's replaced. TestServer replaces Kestrel through the same features contract. Arrange, act, assert, and prove every fix red then green, row by row.

Ten. To contribute: pick a help-wanted issue in one area, agree the approach on the issue first, prefer behavior fixes over public API changes, build only your area after restore and activate, follow nearby code and tests exactly, and target main.

That's ASP.NET Core from the ground up. When you next read a file in this repository, ask the two questions this whole episode was built on: where does this code come from, and who calls whom?
