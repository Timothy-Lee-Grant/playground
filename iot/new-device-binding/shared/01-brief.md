## 1. The task in one paragraph

There is **no upstream issue**: this is a contribution nobody asked for. We add a new device binding for the
**Bosch BMP390** barometric pressure + temperature sensor (and the older **BMP388**, which is register-compatible
and differs only in its chip ID) to dotnet/iot as `src/devices/Bmp3xx/`. dotnet/iot welcomes new bindings
(roadmap item 1: "Add bindings for more devices"; `src/devices/README.md`: "Anyone can contribute a binding.
Please do!"), and every new-binding PR from #2300 to #2616 has landed except one opened 2026-10-03. Timothy will
announce the work with a short proposal issue **after** the sensor works on his Raspberry Pi (G2), then open the
PR after his teach-back (G3).

## 3. The chip, as far as we know (verify every row against the datasheet in plan Step 0)

Source: Bosch reference driver `bmp3_defs.h` / `bmp3.c` @ `db4cf8e`. Datasheet: BST-BMP390-DS002
(https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmp390-ds002.pdf).

| Item | Value |
|---|---|
| I2C address | `0x76` (SDO low) / `0x77` (SDO high) |
| Chip ID register `0x00` | `0x60` = BMP390, `0x50` = BMP388 |
| `ERR_REG` `0x02` | bit0 fatal, bit1 cmd_err, bit2 conf_err |
| `STATUS` `0x03` | bit4 cmd_rdy, bit5 drdy_press, bit6 drdy_temp |
| `DATA_0..5` `0x04..0x09` | pressure xlsb, lsb, msb, then temperature xlsb, lsb, msb (24-bit, little-endian) |
| `PWR_CTRL` `0x1B` | bit0 press_en, bit1 temp_en, bits 4–5 mode: 00 sleep, 01/10 forced, 11 normal |
| `OSR` `0x1C` | bits 0–2 osr_p, bits 3–5 osr_t (0 = ×1 … 5 = ×32) |
| `ODR` `0x1D` | bits 0–4 odr_sel (0 = 200 Hz … 0x11 = one sample every ~655 s; period = 5 ms × 2^odr_sel) |
| `CONFIG` `0x1F` | bits 1–3 IIR coefficient (0 off, 1, 3, 7, 15, 31, 63, 127) |
| Calibration | 21 bytes from `0x31`; 14 coefficients (table in `plan.md` Step 7) |
| `CMD` `0x7E` | `0xB6` = soft reset (wait ~2 ms, then check `ERR` cmd_err) |
| Measurement time | 234 µs + (392 + 2^osr_p × 2000) µs if pressure on + (313 + 2^osr_t × 2000) µs if temperature on |
| Valid output range | −40…85 °C; 30 000…125 000 Pa (Bosch clamps to these; datasheet operating range 300–1250 hPa) |

## 4. Constraints

- **Only one active upstream PR at a time:** Timothy's PR #2611 (iot#2328) is open. Nothing upstream (G2) until
  he says #2611 is settled or he chooses to go ahead anyway.
- **Clean room:** Bosch's driver is BSD-3. It may be built and run **outside the fork** as a test oracle, but
  **no Bosch code, comments or structure enter the fork.** Implement from the datasheet; cite datasheet sections.
- **Don't hand-edit generated files:** `src/devices/Device-Index.md` and the categorized list in
  `src/devices/README.md` are generated by `tools/device-listing` (TM1650 #1855 broke the build doing this).
- **Build rules:** `TreatWarningsAsErrors`, StyleCop (copyright header on every file), XML docs required on every
  public member of non-test projects (CS1591), `Nullable` enabled, `net8.0`.
- **Test projects** must be named `*.Tests.csproj` under `src/devices/**` (that's how `build.proj` finds them for CI).
- **AI disclosure:** dotnet/iot has no written policy; Timothy discloses briefly in the PR description (as on #2611).
  No AI co-author trailers in commits unless he asks.
- **Competing work:** none found as of 2026-10-04 (no `Bmp3`/`BMP388`/`BMP390` folder or PR #2300–#2616).
  Upstream *issues* were not searched; Step 0 re-checks PRs, Timothy checks issues before G2.

## 5. How to build and test (worked on macOS for iot#2328, SDK 10.0.302)

```bash
cd develop/iot
dotnet build src/devices/Bmp3xx/tests/ --no-incremental      # builds binding + tests; 0 warnings required
dotnet test  src/devices/Bmp3xx/tests/ --no-build
dotnet build src/devices/Bmp3xx/samples/
dotnet publish src/devices/Bmp3xx/samples/ -c Release -r linux-arm64 --self-contained -o /tmp/bmp3xx-sample   # for the Pi (linux-arm on a 32-bit OS)
```

The full `./build.sh` (30–45 min, Arcade feeds) is **not** needed; CI runs it on the PR.
