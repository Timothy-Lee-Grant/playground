## 4. Discoveries
- **verified** (`evidence/001`): the Button tests build and pass on Timothy's Mac (Darwin arm64). Inside the repo,
  `global.json` resolves SDK **10.0.302** (installed: 9.0.303, 10.0.302, 11.0.100-preview.5). The `net8.0` tests run on
  the installed .NET 8.0.13 runtime.
- **verified** (command output this session, not saved to a file): the fork has `origin` = Timothy-Lee-Grant/iot
  (partial clone, `blob:none`) and `upstream` = dotnet/iot, with upstream already fetched. It is on `main` @ `1eb0b2f6`,
  the same commit the brief was written against.
- **unverified** (code reading): brief §3's two broken paths match the code. `ButtonBase.IsPressed` starts `false`
  (`ButtonBase.cs:73`). The `GpioButton` constructor opens the pin and registers the both-edges callback
  (`GpioButton.cs:87-91`) but never reads the pin. `PinStateChanged` (`:109-136`) looks only at the edge type,
  never the level. `HandleButtonReleased` has the guard `if (_debounceTime.Ticks > 0 && !IsPressed) return;`
  (`ButtonBase.cs:126`), which swallows the first release when debounce is on.
- **unverified, new (not in the brief):** the fix has an ordering question besides P1's timing question. If the
  pin is read **before** `RegisterCallbackForPinValueChangedEvent`, an edge between the read and the registration
  is lost. If it is read **after**, an edge callback can run at the same time as the constructor's read. This is
  the classic firmware "sample the level vs. enable the interrupt" race.
- **unverified, minor:** `GpioButton.cs:72-73` assigns twice inside the ternary (`_gpioPinMode = _gpioPinMode = ...`).
  Harmless and out of scope.
