## Part one: the problem OpenTelemetry solves

Start with a user complaint. "Checkout took nine seconds at two minutes past two." Your system is five services. A gateway, which is your YARP proxy. An orders service. A payments service. An inventory service. A database. And a message queue between two of them. Each service writes its own log file, on its own machine.

To answer "where did the nine seconds go?", you'd have to find the gateway's log line for that request, using the time and the URL, and hope the clocks on the machines agree. Then you'd have to guess which line in the orders service's log is the same request, because nothing shared connects them. Then repeat that for every hop, including the hop through the queue. And even if you found every line, you still wouldn't know how long each hop took, unless someone happened to log both the start and the end.

In a single program, this problem doesn't exist. A debugger or a stack trace or a profiler shows you the whole story in one place. The key idea is this: **the moment a request crosses a process boundary, its story gets scattered across machines, and nothing in the request itself connects the pieces unless someone deliberately adds that connection.**

Observability is the name for being able to answer questions about a running system from the data it already sends out, including questions you didn't know you'd need to ask. Operators ask three kinds of questions, and each one has its own kind of data, which OpenTelemetry calls a signal.

The first question is "is something wrong, and how much?" How many requests per second, what percentage fail, how slow is the slowest one percent. That's answered by **metrics**: numbers aggregated over time.

The second question is "where did this one request spend its time, across all the services?" That's answered by **traces**. A trace is the whole story of one request, made of **spans**. Each span is one timed operation, like "the orders service handled a POST", or "the orders service ran an insert against the database". Spans point at their parent span, so they form a tree, and a trace viewer draws that tree as a waterfall of bars, one under the other, each one as long as the operation took.

The third question is "what exactly happened at that moment?" That's answered by **logs**: the timestamped text records you already know.

The power comes from connecting the three. Every span in one trace shares one ID, the trace ID. Every log line written while a span was active can carry that same trace ID. And metrics can carry a few sample trace IDs, called exemplars, so a spike on a latency chart leads you to an actual slow request. One ID ties the three signals together.

Why did this need a standard? Before OpenTelemetry, every monitoring vendor shipped its own agent, its own programming interface and its own wire format. That had two bad consequences. First, a library author couldn't add tracing to their library, because whose interface should the library call? Picking one vendor would force that vendor on every user of the library. Second, switching vendors meant rewriting the telemetry code in every service. OpenTelemetry fixes both by splitting the job in two. Producing telemetry happens through a vendor-neutral interface that costs almost nothing when nobody is listening, so libraries can use it freely. Shipping and storing it happens through pluggable exporters and one standard wire format that every vendor now accepts.

A short history. Two earlier projects, OpenTracing and OpenCensus, competed for a few years. In 2019 they merged into OpenTelemetry, under the Cloud Native Computing Foundation, the CNCF, which is the same foundation that hosts Kubernetes and Prometheus. Tracing, metrics and logs became stable over the next few years. In May 2026, OpenTelemetry became a CNCF **graduated** project, the foundation's most mature tier.

Recap of part one. When requests cross processes, their story scatters. Observability means answering questions from data the system already sends. There are three signals: metrics for "how much", traces made of spans for "where did this request go", and logs for "what exactly happened", tied together by the trace ID. OpenTelemetry exists so that libraries can produce telemetry without picking a vendor, and so that apps can switch vendors without rewriting code.

## Part two: what OpenTelemetry is, and what it is not

OpenTelemetry is several things at once, so let's list them.

It's a **specification**: language-neutral rules, written in prose with MUST and SHOULD, that say what every implementation has to do. When a reviewer on a pull request says "the spec says", this is the document they mean. Let's give it a character name: **the Charter**.

It's a set of **semantic conventions**: the agreed names for things. The name of the attribute holding an HTTP method is http dot request dot method. The route template that matched a request is http dot route. The name of the server latency metric is http dot server dot request dot duration. Let's call the conventions **the Dictionary**. Without a shared dictionary, every team's dashboards would only work with that team's own names.

It's a wire format called **OTLP**, the OpenTelemetry Protocol. It's protobuf-encoded data sent over gRPC, usually to port 4317, or over plain HTTP, usually to port 4318.

It's a set of **APIs and SDKs** in about a dozen languages, C#, Java, Go, Python, JavaScript and others.

It's a large collection of **instrumentation libraries**, which make popular frameworks and clients emit telemetry: ASP.NET Core, HttpClient, SQL clients, Redis, Kafka and so on.

And it's **the Collector**: a standalone program, written in Go, that receives telemetry, processes it and forwards it. Let's call the Collector **the Sorting Office**.

Now the part people get wrong. A common misconception is that OpenTelemetry is a monitoring tool, like Grafana. Actually, OpenTelemetry stops at the wire. It doesn't store telemetry, query it, draw it, or send alerts. Those jobs belong to a backend: Jaeger, Prometheus, Grafana, Azure Monitor, or, for local development, the .NET Aspire dashboard. Let's call whatever backend you use **the Archive**. When you see a beautiful trace waterfall, OpenTelemetry made the data, and the Archive drew it.

A second misconception is that OpenTelemetry is automatic. Actually, your own business logic emits nothing until you write code that starts a span, or until a library you call does it for you. Instrumentation libraries cover the frameworks; they don't know anything about your "place order" logic.

Now the family of repositories, because you'll be navigating between them. There are three language-neutral repositories: the specification, the semantic conventions, and the protobuf definitions of OTLP. There are two Collector repositories, the core Collector and the Collector contrib with hundreds of plug-in components. Then each language has its own group of maintainers, called a SIG, a special interest group, with its own repositories.

For .NET, there are three. **opentelemetry dash dotnet** is the core: the API extensions, the SDK, and the required exporters, meaning OTLP, the console exporter, an in-memory exporter for tests, and a few others. **opentelemetry dash dotnet dash contrib** holds everything optional: about fifty components, mostly instrumentation libraries for specific frameworks, plus detectors that figure out what machine or cloud you're running on, plus extra exporters such as one for InfluxDB. And **opentelemetry dash dotnet dash instrumentation** is a separate agent that instruments an app without any code changes, by hooking into the runtime at startup. You can ignore that third one for now.

Why split core from contrib? Core holds what the specification requires every language to provide, and it's released as one unit with one version number. Contrib holds optional pieces, and each one ships on its own schedule with its own named owners, listed in a file called component underscore owners dot yml in the dot github folder. This is like the split you met in ASP.NET Core between the shared framework, which ships as one slow-moving, long-supported unit, and the separately shipped NuGet packages that move faster. Here's where that comparison stops: in contrib, the first reviewer of a change is the component's owner, not the core maintainers. If you work on the InfluxDB exporter, you talk to its owner first.

Recap of part two. OpenTelemetry is a Charter, which is the specification; a Dictionary, which is the semantic conventions; a wire format, OTLP; SDKs in many languages; instrumentation libraries; and a Sorting Office, the Collector. It is not the Archive: storage and display belong to backends. In .NET, core holds the required pieces and releases them together, and contrib holds about fifty optional components, each with its own owners.

## Part three: the signals, precisely

Let's make each signal precise, because the code is organized around them.

A **span** has a trace ID, which is sixteen bytes, written as thirty-two hexadecimal characters, and shared by every span in the trace. It has its own span ID, eight bytes, written as sixteen hex characters. It has a parent span ID, which is empty for the first span of a trace, the root. It has a name, like "GET slash orders slash curly-brace id". It has a kind, which says which side of a call it represents: server, client, internal, producer or consumer. It has a start time and an end time. It has attributes, which .NET calls tags: key-value pairs like http dot request dot method equals GET. It can have events, which are timestamped moments inside the span, like an exception being thrown. It can have links, which say "related to that other span, but not my parent", for example when a batch job processes fifty queued messages that each came from a different trace. And it has a status: unset, ok, or error.

The kinds come in pairs across a call. When the gateway calls the orders service, the gateway has a **client** span for the outgoing call, and the orders service has a **server** span for handling it, and the server span's parent is the client span. That pairing across a process boundary is exactly what part eight is about.

A **metric** is different in a way that surprises people. It isn't a list of events. The SDK **aggregates** measurements in memory and periodically exports only the aggregate. For a counter, that's a running sum. For a histogram, it's counts per bucket, plus the sum, minimum and maximum. And it keeps one aggregate per unique combination of attributes. So a request-duration histogram might hold one row for GET on the orders route with status 200, another for GET on the orders route with status 404, and so on. In .NET each row is called a metric point. Because only aggregates leave the process, metrics cost about the same whether you have ten requests a second or ten thousand. Spans, by contrast, cost something per request.

**Logs** in .NET don't get a new programming interface. You keep using ILogger, exactly as you do today. OpenTelemetry plugs in as one more logging provider, alongside the console logger, turns each log call into an object called a LogRecord, stamps it with the current trace ID and span ID, and exports it.

**Baggage** is a set of key-value pairs that travels with a request across services, like tenant equals contoso. It isn't telemetry on its own; nothing records it unless code copies it onto a span or a log. It rides in its own HTTP header, called baggage. Let's call baggage **the Sticky Note**: a note stuck to the request that every service along the way can read.

A **resource** describes who produced the telemetry: the service name, its version, the host name, the container or Kubernetes pod. It's attached to each batch that gets sent, not to each span. Let's call the resource **the Return Address**. If you don't set a service name, the .NET SDK uses the words "unknown underscore service", a colon, and the process name, which is a clear sign that someone forgot to configure it. Setting the service name is the first thing every real app should do.

And there's a fourth signal on the way, profiling, which records which functions use CPU and memory. It entered public alpha in 2026. It isn't in the .NET SDK in any stable form, so you can set it aside.

Recap of part three. A span is one timed operation with a trace ID, its own ID, a parent ID, a name, a kind, times, attributes, events, links and a status, and client and server spans pair up across a call. A metric is an in-memory aggregate per attribute combination, exported periodically. Logs use ILogger, stamped with the trace ID. Baggage, the Sticky Note, travels with the request. The resource, the Return Address, says who sent it, and forgetting the service name shows up as unknown service.

## Part four: the .NET twist, and where the code comes from

Here's the most important thing that makes .NET different from every other OpenTelemetry language. In Java or Python, a library that wants to create a span calls the OpenTelemetry API package for that language. In .NET, it calls a class called **ActivitySource**, in the System dot Diagnostics namespace, and that class ships inside the .NET runtime itself. The span it creates is a class called **Activity**.

The reason is history. .NET had a class called Activity years before OpenTelemetry existed. ASP.NET Core and HttpClient already used it to carry correlation IDs. When OpenTelemetry came along, the .NET runtime team and the OpenTelemetry .NET maintainers agreed, around .NET 5 in 2020, to extend Activity until it matched the OpenTelemetry span model exactly, and to add ActivitySource and a matching listener type. Later, in .NET 6, they did the same for metrics, with a class called Meter. The payoff is big. The runtime, ASP.NET Core, HttpClient, SQL client, gRPC, SignalR and Blazor can all emit OpenTelemetry-shaped telemetry **without depending on any OpenTelemetry package at all**.

So here's the translation you'll use on every page of this code base. What the specification calls a **tracer**, .NET calls an **ActivitySource**. What the specification calls a **span**, .NET calls an **Activity**. Span attributes are Activity tags. The span context, meaning the trace ID, span ID and flags, is a struct called ActivityContext. The "current span" is a static property called Activity dot Current. A **meter** is a Meter, and the instruments are classes like Counter and Histogram, in the System dot Diagnostics dot Metrics namespace. The logs API is ILogger. All of those come from the runtime or from Microsoft's own extension libraries, not from OpenTelemetry.

What does come from OpenTelemetry? Two NuGet packages, mainly. The **API package**, named OpenTelemetry dot Api, holds the few things the runtime doesn't have: the Baggage class, and the propagators, which are the classes that write context into headers and read it back. And the **SDK package**, named just OpenTelemetry, holds the providers, the sampler, the processors, the batching machinery and the base class for exporters. Then each exporter and each instrumentation library is its own package on top.

A common misconception is that you're supposed to use OpenTelemetry's own Tracer and TelemetrySpan classes in .NET. Those classes do exist in the API package, but they're a thin wrapper, which the project calls a shim, over Activity, meant for people porting code from other languages. The API's own documentation says the SDK operates entirely with Activity. Use ActivitySource and Activity.

Now, since where-does-code-come-from has felt fuzzy, let's walk through it layer by layer for an ordinary ASP.NET Core app with OpenTelemetry turned on. There are three sources of code in that process.

The first source is the **.NET runtime's shared framework**, installed once per machine, with no NuGet download involved. Inside it is an assembly, a compiled DLL, called System dot Diagnostics dot DiagnosticSource. That one assembly holds Activity, ActivitySource, the activity listener type, Meter and the metric instruments, and the runtime's own header-writing helper, called DistributedContextPropagator.

The second source is the **ASP.NET Core shared framework**, also installed once per machine. Its hosting assembly creates an Activity for every incoming request, from an ActivitySource named Microsoft dot AspNetCore, whether or not OpenTelemetry is installed.

The third source is **NuGet packages**, downloaded at build time and copied next to your app. These are OpenTelemetry dot Api, the SDK called OpenTelemetry, the hosting integration called OpenTelemetry dot Extensions dot Hosting, the OTLP exporter, and from the contrib repository, the ASP.NET Core instrumentation package.

Three things to make sharp. First, the using directive at the top of a file, "using System dot Diagnostics", grants nothing. It only lets you write Activity instead of System dot Diagnostics dot Activity. The class is reachable because your project targets .NET, whose shared framework contains that assembly. On very old targets, like .NET Framework, the same assembly has to arrive as a NuGet package instead, which is why it shows up in the OpenTelemetry repository's package list.

Second, the split between the API package and the SDK package is the same idea as the abstractions split you saw in ASP.NET Core, where contracts live in one assembly and the code that fulfills them lives next door. A **library** references only the API, or nothing beyond the runtime's ActivitySource. Only the **application** references the SDK and the exporters. Why? Because a library can't know which exporter, which sampling rate or which vendor the application will choose, and it has to cost nothing when telemetry is turned off. The repository's own guidance file for AI agents, called AGENTS dot md, describes this as a strict three-layer design: the no-op API layer, then the SDK, then the exporters.

Third, versions. The core packages are always released together with the same version number, even if only one of them changed. And a library built against API version one point something works with any SDK that has the same major version and an equal or newer minor version.

Recap of part four, which is also the end of episode one. In .NET, ActivitySource is the tracer, Activity is the span, Meter is the meter, and ILogger is the log API, and all of them come from the runtime or Microsoft's extension libraries, not from OpenTelemetry. That lets Microsoft's own frameworks emit telemetry with no OpenTelemetry dependency. OpenTelemetry supplies the API package, with baggage and propagators, and the SDK package, with everything that listens, samples, batches and exports. Libraries use only the API; applications add the SDK. And the using directive only shortens names; it never grants access.

## Part five: the cast of characters

Episode two starts here. The rest of this lecture follows one span on a journey, so first, meet everyone it will pass through. Each character is a real type in the code. Learn the job first; the class name is just a label.

**The Reporter** is ActivitySource. Every library creates one, with a name, like "Orders dot Domain", or "Microsoft dot AspNetCore", and keeps it in a static field for the life of the process. The Reporter's habit is important: before creating anything, it asks "is anyone listening to me?" If nobody is, it creates nothing at all.

**The Timecard** is Activity, one span. It records the operation's name, its IDs, start and stop times, tags, events and status.

**The Case File** isn't a class at all. A trace is simply every Timecard, in every service, that shares the same trace ID. No single object holds a whole trace, and no single service ever sees one.

**The Clipboard** is Activity dot Current. It holds "the Timecard currently in progress" for this particular flow of work, so that a new Timecard knows who its parent is without anyone passing the parent around. Part nine explains how the Clipboard follows a request across threads.

**The Bureau Chief** is the tracer provider in the SDK, the class TracerProviderSdk. It's built when you configure tracing. It owns everything on the listening side: the sampler, the processors, the exporter. It decides which Reporters to listen to, based on the source names you added.

**The Bureau Chief's phone line** is ActivityListener, a runtime type that the Bureau Chief creates and registers with the runtime. It's just an object holding four callbacks, four delegate-typed properties. One answers "should I listen to this Reporter?" One answers "should this particular span be recorded?" One is called when a span starts. One is called when a span stops.

**The Selector** is the Sampler. For each new span, it decides one of three things: record it and export it, record it but don't export it, or drop it. The default Selector is called ParentBased, wrapped around AlwaysOn. Part eleven explains why.

**The Desk Clerk** is a processor, the base class is BaseProcessor of Activity. Every recorded span is handed to the Desk Clerks twice, once when it starts, through a method called OnStart, and once when it ends, through OnEnd. A Clerk can add tags, filter, or hand the span on.

**The Mailroom** is a particular kind of Desk Clerk, the batch export processor. When a span ends, the Mailroom drops it into **the Out-Tray**, which is a bounded ring buffer, a fixed-size circular queue, with room for 2048 spans by default.

**The Mail Carrier** is a background thread owned by the Mailroom. It sleeps until either 512 spans are waiting in the Out-Tray, or five seconds pass, whichever comes first. Then it wakes up, takes up to 512 spans as one batch, and hands them to the Packer.

**The Packer** is the exporter, a class derived from BaseExporter. The OTLP exporter turns a batch of spans into protobuf bytes and sends them to the Sorting Office or straight to the Archive. The console exporter writes them to the terminal instead.

**The Stamper** is the propagator. On the way out of a service, it writes the current trace's context onto the outgoing request, which is called **inject**. On the way into the next service, it reads that context back, which is called **extract**. What it writes is a header called traceparent, which we'll call **the Stamp**.

**The Annotator** is an instrumentation library, such as the ASP.NET Core instrumentation from the contrib repository. Its main class for incoming requests is called HttpInListener. ASP.NET Core creates the request's span itself; the Annotator adds the standard tags from the Dictionary and sets the standard name.

On the metrics side, there's **the Meter Panel**, which is a Meter plus its instruments; **the Ledger**, which is the SDK's in-memory store of aggregates, the class AggregatorStore, with one row, a MetricPoint, per attribute combination; and **the Auditor**, the periodic metric reader, which visits the Ledger every sixty seconds by default and hands a snapshot to a Packer.

On the logs side, there's **the Scribe**, which is ILogger, the same character from the ASP.NET Core lecture, and **the Scribe's Copier**, which is the OpenTelemetry logger provider that copies each log call into a LogRecord.

And outside the process, as you know, are the Sorting Office, which is the Collector, and the Archive, which is the backend.

Here's how they relate, in words. At startup, the Bureau Chief is built. It builds its Selector and its Desk Clerks, including the Mailroom with its Out-Tray, its Mail Carrier and its Packer, and it plugs its phone line into the runtime. At run time, a Reporter asks the phone line whether anyone's listening, then asks the Selector whether to record, creates a Timecard, and clips it to the Clipboard. When the Timecard stops, the phone line tells the Desk Clerks, the Mailroom drops it in the Out-Tray, and later the Mail Carrier hands a batch to the Packer, which sends it across the network.

Recap of part five. Reporter is ActivitySource; Timecard is Activity; the Case File is all Timecards sharing a trace ID; the Clipboard is Activity dot Current. The Bureau Chief is the tracer provider, with its phone line, the ActivityListener, its Selector, the sampler, and its Desk Clerks, the processors. The Mailroom's Out-Tray holds 2048 spans; its Mail Carrier ships at 512 or every five seconds; the Packer is the exporter. The Stamper writes and reads the traceparent Stamp; the Annotator adds standard tags. Metrics have the Meter Panel, the Ledger and the Auditor; logs have the Scribe and the Scribe's Copier.

## Part six: startup, and what AddOpenTelemetry really does

You know the shape of an ASP.NET Core app: create a builder, register services, build the app, add middleware, run. In a real app, OpenTelemetry setup looks like this, read aloud. builder dot Services dot AddOpenTelemetry. Then ConfigureResource, adding a service named "orders", which is the Return Address. Then WithTracing, and inside it, add ASP.NET Core instrumentation, add HttpClient instrumentation, and add source "Orders dot Domain", which is your own Reporter. Then WithMetrics, with ASP.NET Core instrumentation and your own meter. Then WithLogging. And finally UseOtlpExporter, which sets up one OTLP Packer for all three signals.

Every one of those calls is an extension method, a static method written with dot-call syntax, which means none of them is a member of the services collection. They come from the OpenTelemetry packages and plug themselves in, the same way every ASP.NET Core feature does.

Now the key idea of this part. **Setup only records intentions. Nothing that listens exists until the host starts.** Let's go phase by phase.

In the **builder phase**, when you call AddOpenTelemetry and the With and Add methods, OpenTelemetry registers configuration callbacks and singleton services in the dependency injection container. No tracer provider exists yet. No listener exists. If code started an Activity right now, nobody would be listening, and StartActivity would return null.

In the **build phase**, when you call builder dot Build, the service provider, the Supply Room from the ASP.NET Core lecture, gets built. Still nothing is constructed, because singletons in the Supply Room are created lazily, the first time someone asks for them.

In the **run phase**, when you call app dot Run, the host starts its hosted services before Kestrel starts accepting requests. AddOpenTelemetry registered a tiny hosted service called TelemetryHostedService. Its entire start method calls one initializer, and the comment in the source says, quote, "The sole purpose of this HostedService is to ensure all instrumentations, exporters, etc., are created and started." Asking for the providers makes the Supply Room construct the Bureau Chief. The Bureau Chief builds its Selector, its Desk Clerks and its Packer, and plugs its phone line into the runtime. From that moment, Reporters have someone listening.

In the **shutdown phase**, the host stops and the service provider is disposed. Because the provider is a singleton that the container created, the container owns it, so disposing the container disposes the providers. A provider's disposal shuts down its processors, which tells the Mailroom to ship whatever is still in the Out-Tray, and then tells the Packer to close its connections.

Here's what's different from what you already know, and it's important. **OpenTelemetry is not middleware.** It doesn't sit in the request pipeline, and nothing in the pipeline calls it per request. It's a **subscriber**. It registers callbacks with the runtime's static machinery, and then the runtime calls those callbacks whenever any code, ASP.NET Core, HttpClient, your code, starts or stops an Activity from a source the Bureau Chief chose to listen to. If you remember the events lecture: ActivitySource is the publisher, the Bureau Chief is the subscriber, and the "event" is a span starting or stopping. Where that comparison stops: the subscription isn't made with the event keyword and plus-equals; it's made by handing a listener object to a static method called ActivitySource dot AddActivityListener, which adds it to a list the runtime keeps for the whole process.

Now, what this does not do, because it's easy to give the abstraction credit for more than it does. A common misconception is that adding ASP.NET Core instrumentation traces "everything in the app". Actually, it listens to the one span that ASP.NET Core itself creates for each request, and decorates it. It doesn't create spans for your business logic, your database calls or your background services. Every other span exists only because some library or your own code called StartActivity, **and** you added that library's source name.

One more thing you'll see. Almost every option can also be set with environment variables defined by the specification, like OTEL underscore SERVICE underscore NAME, or OTEL underscore EXPORTER underscore OTLP underscore ENDPOINT. And a newer, experimental package lets you configure the whole SDK from a YAML file, which the specification calls declarative configuration. The most recent commits on the main branch are about that package.

Recap of part six. The With and Add calls only register intentions in the dependency injection container. Building the app constructs nothing. When the host starts, a tiny hosted service asks for the providers, which makes the Bureau Chief exist and plug its phone line into the runtime. At shutdown, disposing the container disposes the providers, which flushes the Out-Tray. OpenTelemetry is a subscriber, not middleware. And instrumentation only decorates spans that a framework creates; your own code's spans need your own StartActivity and your own source name.

## Part seven: one span's life inside one process

Now the main event. We'll follow one span, step by step, saying who hands what to whom, and what state everything is in after each step.

The code is a method in the orders service called PlaceOrderAsync. At the top of the class, there's a static, read-only ActivitySource named "Orders dot Domain". Inside the method, the first line says "using var activity equals Source dot StartActivity, with the name PlaceOrder". The next line says "activity, question-mark-dot, SetTag, order dot item underscore count, and the number of items in the cart". Then it awaits a call that saves the order to the database. Then another question-mark-dot SetTag, with the order's ID. Then it returns the order.

Before the journey, let's expand two pieces of syntax into plain if-else, because neither one works like anything in C. The question-mark-dot in "activity, question-mark-dot, SetTag" means: if activity is not null, call SetTag on it; otherwise, do nothing at all, and don't even evaluate the arguments. C has no operator like that; you'd write the if by hand. And "using var activity equals" something means: when this block of code ends, by any route, including an exception, call activity dot Dispose. The compiler writes a try and a finally for you, and in the finally, it says: if activity is not null, call Dispose. In C, you'd write a cleanup label and jump to it from every error path. Here's where that comparison stops: Dispose on an Activity doesn't free memory. The garbage collector still owns the memory. Disposing an Activity **stops the span**: it records the end time and tells the listeners that the span has stopped.

Now, the journey. At the start, a request for "POST slash orders" is already in progress. ASP.NET Core created its server span when the request arrived, and that span is on the Clipboard. Let's call it span S.

Step zero happened long before, at startup. The Bureau Chief plugged in its phone line, and its "should I listen" callback said yes to the source named Orders dot Domain, because you added that name.

Step one. The Reporter, Orders dot Domain, is asked to start an activity called PlaceOrder. It checks its list of listeners. One listener is interested. So it continues. At this point, no Timecard exists yet, and the Clipboard still holds S.

Step two. The Reporter calls the phone line's sampling callback, which hands the Selector the would-be parent, which is S's context, plus the trace ID, the name, the kind and any initial tags. The default Selector is ParentBased around AlwaysOn: it sees there's a parent, sees the parent is sampled, and copies that decision. The answer is "record and sample". Still no Timecard, and the Clipboard still holds S.

Step three. The Reporter creates the Timecard. Let's call it P. P gets the **same trace ID as S**, its own new span ID, and S's span ID as its parent ID. It's started, and starting it puts it on the Clipboard. Now the variable activity holds P, not null, and the Clipboard holds P.

Step four. The runtime calls the phone line's "activity started" callback. The Bureau Chief's code checks a property on P called IsAllDataRequested, which is true because the Selector said record, and then calls OnStart on its Desk Clerks. The Clipboard still holds P.

Step five. Your code runs. It sets tags, and awaits the database save. If the database client is instrumented, its span is created while P is on the Clipboard, so the database span becomes P's child, without anyone passing P to the database code. The Clipboard follows the await across threads, which part nine explains.

Step six. The method ends, so the using statement calls Dispose on P, which stops it. P's end time is recorded, and the Clipboard goes back to S.

Step seven. The runtime calls the phone line's "activity stopped" callback. The Bureau Chief checks IsAllDataRequested again, and calls OnEnd on its Desk Clerks. One of them is the Mailroom, which tries to add P to the Out-Tray. Say there were n spans waiting before; now there are n plus one.

Step eight. The Mailroom looks at the count that came back from adding P. If that count just reached 512, which is the maximum batch size, it wakes the Mail Carrier immediately. Otherwise, it does nothing, and the Mail Carrier will wake on its own five-second timer. There's a nice comment in the source explaining why it only signals at exactly 512 rather than on every add: signaling the thread for every span would cost every request a trip into the operating system's kernel, for nothing.

Step nine. The Mail Carrier wakes up. It's a dedicated background thread, and its name is built from the processor and exporter names, OpenTelemetry dash BatchExportProcessor dash OtlpTraceExporter. It takes up to 512 spans as a batch and calls Export on the Packer. This happens on the Mail Carrier's thread, not on any request's thread.

Step ten. The Packer, the OTLP trace exporter, serializes the batch into protobuf, using a serializer the project wrote by hand rather than a generated library, and sends it. On modern .NET, the default is gRPC to localhost port 4317; on .NET Framework, the default is HTTP with protobuf to port 4318.

There's one more guard worth knowing. The OTLP exporter sends its data using HttpClient, and HttpClient is itself instrumented. So exporting a span would create a new span, which would be exported, which would create another span, forever. To prevent that, exporters turn on a flag called suppress instrumentation while they work, and the phone line checks that flag and ignores spans created under it. Telemetry about telemetry gets switched off.

Now, what happens when the Out-Tray is full? Say the Collector is down, or the network is slow, and spans end faster than the Mail Carrier can ship them. The source code is blunt about it. If adding to the circular buffer fails, the comment says, quote, "either the queue is full or exceeded the spin limit, drop the item on the floor". It increments a dropped counter and returns false. The key idea is **drop the newest span, never block the caller**. A web request must never wait because the telemetry backend is slow. Losing some telemetry is the lesser evil. That's backpressure: what a system does when a producer is faster than a consumer. There are three classic answers, block the producer, drop the new item, or evict the oldest item, and that exact three-way choice is the subject of the InfluxDB exporter issue on your list, whose exporter had no bound at all.

A firmware comparison genuinely helps here, and it's bounded. It's like a ring buffer filled by an interrupt handler: the handler can't wait, so when the buffer is full it drops data. Where the comparison stops: in firmware, a ring buffer usually has exactly one producer and one consumer, and you can use simple head and tail indexes. Here, any of hundreds of thread-pool threads can end a span at the same moment, so adding to the buffer uses atomic compare-and-exchange operations from the Interlocked class, with spinning, instead of plain index updates.

And now, what this machinery does not do. It doesn't measure anything you didn't wrap: a span's duration is exactly from start to stop. It doesn't make spans free when someone is listening: each recorded span costs allocations and CPU, which is why sampling exists. It never sends anything synchronously, so your request never waits on the network for telemetry. And it doesn't keep data forever if the backend is down: the OTLP exporter retries transient failures, and has optional persistent storage, but by default, data that can't be sent is eventually lost.

Here's a small experiment for later, and remember, its result is a prediction. Build a tiny console app with a tracer provider that listens to a source called Demo dot Shop and writes to the console. Start a span called PlaceOrder, and inside it, a span called ChargeCard. The prediction is that ChargeCard prints first, because spans are exported when they end, not when they start, and that both share one trace ID, with ChargeCard's parent being PlaceOrder. Then change the listened-to source name to something else. The prediction is that nothing prints, and the PlaceOrder variable is null. Then switch the sampler to AlwaysOff. The prediction there is subtle: PlaceOrder is **not** null, but ChargeCard **is**. The reason is in a small function in the SDK: for a root span, or a span whose parent came from another process, a "drop" decision still creates a context-only Activity, which records nothing but keeps the trace ID alive for propagation. For a span whose parent is local and unsampled, a "drop" decision creates nothing. So there are three different outcomes: no listener means no object; a drop decision means either a context-only object or no object, depending on the parent.

Recap of part seven. The Reporter checks for a listener, the Selector decides, the Timecard is created with the parent's trace ID and placed on the Clipboard, your code runs, and Dispose stops it and restores the Clipboard. The phone line's stopped callback hands it to the Desk Clerks; the Mailroom puts it in the Out-Tray; the Mail Carrier wakes at 512 spans or every five seconds and hands a batch to the Packer, which sends OTLP to port 4317. Exporters suppress their own instrumentation. When the Out-Tray is full, the newest span is dropped and counted, never blocking the request.

## Part eight: one trace across two processes

Here's the rule for this part. **Services share nothing but the bytes on the wire. A trace spans two services only because the caller writes the current span's context into a header, and the callee reads it back and uses it as the parent of its own span.**

That header, the Stamp, is defined by a W3C standard called Trace Context, and its name is traceparent. Its value has four parts separated by dashes. First, a version, which today is always zero zero. Second, the thirty-two-character trace ID. Third, a sixteen-character span ID, and this is the **caller's** span ID, the ID of the client span that's making the call. Fourth, two characters of flags, where zero one means "sampled" and zero zero means "not sampled". There's an optional second header, tracestate, for vendor-specific data, and baggage, the Sticky Note, travels in its own header called baggage.

Now the journey, step by step. Service A is the gateway. On its Clipboard is its server span, G, for the incoming request.

Step one: code in A calls HttpClient's SendAsync. Step two: HttpClient itself creates a client span, C, from an ActivitySource named System dot Net dot Http. C's parent is G, and it has G's trace ID. Step three: the Stamper injects: it writes the traceparent header onto the outgoing request, containing the trace ID and **C's** span ID, with the sampled flag. The request travels over the network.

Step four: in service B, Kestrel parses the incoming request. Step five: ASP.NET Core's hosting layer, B's Stamper, extracts: it reads traceparent and turns it into an ActivityContext with the trace ID, C's span ID as the parent, and a flag saying "this parent is remote", meaning it came from another process. Step six: it starts B's server span, S, from the source named Microsoft dot AspNetCore, with that remote context as its parent. Step seven: the Annotator, OpenTelemetry's HttpInListener, adds the standard tags to S. At the end of the request, once routing has picked a route, it sets S's name to the method followed by the route template, like "POST slash orders". Step eight: S stops and is exported by B's own Mailroom. Step nine: back in A, the response arrives, C stops, and is exported by A's Mailroom.

Notice what that means. Both services export **separately**, maybe to different Collectors, maybe seconds apart. The Archive stitches the Case File together later, by trace ID and parent IDs. A common misconception is that the Collector or the backend connects the spans. Actually, the connection is decided at run time, inside the services, by the parent IDs they put on each span. The backend only groups spans that already share a trace ID. If the header didn't make it across, no backend can repair the trace afterwards.

Here's a subtle point that confuses people reading this code. There are **two Stampers** in a .NET app. The runtime has its own, a class called DistributedContextPropagator, and HttpClient and ASP.NET Core use it themselves, even with no OpenTelemetry installed, writing and reading the W3C traceparent header. OpenTelemetry has its own, in the API package, called TextMapPropagator; once the SDK is set up, its default is a composite of two: W3C Trace Context, and W3C Baggage. The contrib instrumentation libraries bridge the two. On the incoming side, if your configured OpenTelemetry propagator is anything other than plain Trace Context, the Annotator extracts again using OpenTelemetry's Stamper. If that produces a different parent than ASP.NET Core used, which happens if you configured a different header format, like the B3 format from Zipkin, the Annotator creates a **sibling** span with the correct parent, marks the framework's span as not recorded, and exports the sibling instead. It also sets the current baggage from the incoming baggage header. That's a good example of what instrumentation often means: not doing the work from scratch, but **repairing and decorating** what the framework already does.

The same inject-and-extract works for any carrier that holds string key-value pairs, not just HTTP headers. Kafka and RabbitMQ message headers work. The underscore-meta field in an MCP JSON-RPC message works, which is exactly what the MCP C# SDK does, and that's scouted item O. You hand the propagator two small functions, a setter that writes one key, and a getter that reads one key, and it does the rest. The core repository has a complete example called MicroserviceExample: a web API publishes messages to RabbitMQ, a worker service consumes them, and the trace context rides in the message headers, with a Collector and Zipkin in a Docker Compose file.

And here's the experiment that makes this stick, again a prediction until you run it. Run two small ASP.NET Core apps, A calling B, both instrumented. B's server span should share A's trace ID, with A's client span as its parent. Then, in A, add a small HttpClient handler that removes the traceparent header before sending. B should now start a brand-new trace, with no parent: two unrelated Case Files. That is the single most common real-world tracing bug: some hop, a proxy, a queue, a home-grown protocol, doesn't carry the header.

Recap of part eight, which ends episode two. The traceparent Stamp carries version, trace ID, the caller's span ID, and a sampled flag. The caller injects; the callee extracts and makes its server span a child of the caller's client span. Each service exports separately, and the Archive groups spans by IDs that were decided at run time, so a missing header can never be repaired later. The runtime has its own Stamper, used by HttpClient and ASP.NET Core; OpenTelemetry's Stamper defaults to Trace Context plus Baggage; the Annotator bridges them, sometimes by creating a sibling span. And any key-value carrier, including Kafka headers and MCP's meta field, can carry the Stamp.

## Part nine: the Clipboard, AsyncLocal, and the baggage bug

Episode three starts here, with the subtlest idea in the whole project. The rule is: **"current", in Activity dot Current and in Baggage dot Current, means current for this async flow. It's stored in something called AsyncLocal. Values flow down into work you start or await. Changes made inside that child work don't flow back up.**

First, the problem the Clipboard solves. In part seven, the database span became a child of PlaceOrder without anyone passing PlaceOrder to the database code. The database instrumentation simply read Activity dot Current. But "current" can't be an ordinary global variable, because a web server handles hundreds of requests at once on a shared pool of threads. And it can't be per-thread storage either, because when a method awaits something, the rest of that method may resume later on a completely different thread.

The answer is a class called **AsyncLocal**. An AsyncLocal stores its value in the **execution context**, a small object the runtime carries along with each logical flow of async work. When you await, or start a task, the runtime captures the current execution context, and when the continuation runs, on whatever thread, the runtime restores it. So request one might start on thread seven, await, and resume on thread twelve, and still see its own span on the Clipboard. Meanwhile, request two might start on thread nine and later resume on thread seven, and see its own span. Thread seven serves both requests at different moments, and each flow sees only its own value.

There's one more property, and the baggage bug depends on it. The execution context behaves as if it's **immutable**, meaning it never changes in place. Setting an AsyncLocal doesn't modify the existing context; it makes a new context for this flow from here on. A child task gets the parent's context as it was at the moment the child started. If the child then sets the value, it only replaces its own copy. So there are two rules. A parent sets a value and then starts or awaits a child: the child sees the parent's value. A child sets a new value: the parent doesn't see it, even after the child finishes. That second rule is why Activity dot Current "restores itself" so neatly: when a child span stops in a child flow, the parent flow never saw it change.

A firmware comparison, bounded: it's like giving each RTOS task its own copy of a "current transaction" variable in its task control block. Here's where it stops: async flows aren't threads. One thread runs many flows over time, and one flow hops between threads. The "control block" travels with the flow, not with a thread.

Now, the bug, which is issue 7449 in the core repository, and scouted item N. Baggage itself is an immutable value, a struct. But Baggage dot Current doesn't store the baggage directly in the AsyncLocal. It stores a reference to a small, mutable class called **BaggageHolder**, a box with one field inside, and the field holds the baggage. And the setter for Baggage dot Current doesn't replace the box. It finds the existing box and writes the new baggage **into** it.

Let's walk through it, saying the state after every step.

Step one: the parent flow sets Baggage dot Current to tenant equals A. There's no box yet, so the code creates box H, stores a reference to H in the parent's AsyncLocal, and puts tenant equals A inside H. The parent reads tenant equals A.

Step two: the parent starts a child task. The execution context is captured for the child. What gets copied is the **reference** to H, not H itself. Now the parent and the child both point at the same box, H, and it holds tenant equals A.

Step three: the child sets Baggage dot Current to tenant equals B. The setter looks for an existing box, finds H, the shared one, and writes tenant equals B into it. The child reads tenant equals B, as expected. But the parent's AsyncLocal still points at H, so the parent now reads tenant equals B as well. That's the leak.

Step four: the child finishes. Nothing changes back. The parent keeps reading tenant equals B.

If the AsyncLocal had held the baggage value itself, step three would have made a new context just for the child, and the parent would still read tenant equals A. So the key idea is: **the leak is caused by putting a mutable box inside the AsyncLocal, not by AsyncLocal itself.**

Why hasn't it been fixed? Because the leak is also something people rely on. Code that sets baggage inside a helper method, which runs as a child flow, and expects the caller to see it afterwards, works today **because of** the shared box. Changing the behavior would break that code, so the issue is labeled as needing a major version bump. An earlier fix was merged and then reverted, and a later attempt was abandoned. That's as of the September 26 scouting pass, and the box code is unchanged at the commit this lecture checked. The right goal for you here is to reproduce it, not fix it. The experiment is half an hour: one console app that shows a plain AsyncLocal of string not leaking, an AsyncLocal holding a mutable class leaking, and then Baggage dot Current leaking the same way.

One last gotcha. Activity has its own, separate baggage, set with a method called AddBaggage and stored on the Activity itself. OpenTelemetry's Baggage class is stored in the execution context, independent of any Activity. They're two different mechanisms. OpenTelemetry's propagators send OpenTelemetry's Baggage. A common mistake is setting Activity's baggage and wondering why the next service never received it.

Recap of part nine. Activity dot Current and Baggage dot Current are per async flow, using AsyncLocal, which travels in the execution context across awaits and threads. Values flow down to children; a child's changes don't flow back up. The baggage bug happens because the AsyncLocal holds a reference to a shared mutable box, and the setter writes into the box, so parent and child see each other's changes. It isn't fixed because existing code depends on that behavior. And Activity's baggage is not OpenTelemetry's baggage.

## Part ten: metrics, and the word cardinality

The rule for metrics: **instruments report raw measurements; the SDK aggregates them in memory, one row per unique combination of attributes; a reader exports snapshots periodically. Only aggregates ever leave the process.**

The instruments come from the runtime, in System dot Diagnostics dot Metrics. A **Counter** only goes up: requests served, bytes sent. You call Add. An **UpDownCounter** can go up or down: items in a queue, open connections. A **Histogram** records values whose distribution matters, like request duration; you call Record, and the SDK keeps counts per bucket. A **Gauge** records a current value, like a temperature. And there are **observable** versions of these, where instead of calling Add or Record, you give the instrument a callback, and the SDK calls your callback when it's time to collect. Observable gauges are how things like the garbage collector's heap size get reported, and that's the kind of instrument scouted item R would add.

Now the pipeline. Your code calls Add on a counter called orders dot placed, with an attribute payment dot method equals card. The runtime calls the metrics listener that the SDK's meter provider set up at startup. The listener finds the Ledger for that instrument, the AggregatorStore, looks up the row for the attribute combination "payment method equals card", and adds one to that row's sum, using lock-free atomic operations. Another call with payment method equals cash goes to a different row. Then, every sixty seconds by default, the Auditor, the periodic exporting metric reader, takes a snapshot of every row and hands it to a Packer.

Now the most important word in metrics: **cardinality**. Cardinality is the number of distinct attribute combinations for one metric. Every combination is a separate row in memory, and a separate time series in the Archive, and Archives usually charge by time series. A request-duration histogram with method, route template and status code might have five methods times twenty routes times eight status codes, about eight hundred rows. That's fine. Replace the route template with the raw path, slash orders slash 1, slash orders slash 2, and so on, and the number of rows is unbounded: memory grows forever, and the bill explodes. Add a user ID, and it's unbounded and a privacy leak too.

So the SDK protects itself. **Each metric has a cardinality limit, 2000 rows by default.** Once a metric has that many combinations, measurements for any new combination are folded into one reserved row, the overflow row, tagged with an attribute named otel dot metric dot overflow, set to true. The application can change the limit per metric using something called a View.

This is exactly the argument in the YARP span-naming discussion, scouted item L. Using the raw request path as a span name makes span names high-cardinality, because names are used to group spans, and paths can contain IDs and personal data. That's why the HTTP conventions say to name server spans with the route template.

Two more metric ideas, briefly. **Temporality**: with cumulative temporality, each export says "total since the process started", like 1,204, then 1,310, then 1,377. With delta temporality, each export says "since the last export", like 106, then 67. Prometheus expects cumulative, and cumulative is the default. And **Views**: a View lets the application change how an instrument that a library defined gets aggregated: rename it, drop it, keep only some attributes, change the histogram buckets, or change the cardinality limit. The library author chooses what to measure; the application operator chooses how much of it to keep. That split of authority, author versus operator, shows up all over OpenTelemetry.

Finally, a trend worth noticing. Since .NET 8, ASP.NET Core publishes its own metrics, from meters with names like Microsoft dot AspNetCore dot Hosting and Microsoft dot AspNetCore dot Server dot Kestrel. On modern .NET, the contrib package's "add ASP.NET Core instrumentation" for metrics mostly just subscribes to a list of thirteen built-in ASP.NET Core meter names. Instrumentation is moving into the libraries themselves, which the community calls native instrumentation, and the contrib packages shrink to "listen to the right names, and fill gaps for older runtimes". The same trend shows up in tracing: on ASP.NET Core 11 and later, the framework sets the standard route tags on its own spans, and the Annotator steps aside.

Recap of part ten. Counters, up-down counters, histograms, gauges and observable instruments report measurements. The Ledger keeps one row per attribute combination; the Auditor exports snapshots every sixty seconds. Cardinality is the number of combinations; the default limit is 2000 per metric, after which new combinations go into the overflow row. Raw paths and user IDs are the classic cardinality mistakes. Cumulative temporality is the default, and Views let the application reshape library metrics. Instrumentation is moving into the frameworks themselves.

## Part eleven: logs, sampling, the Collector, and the conventions

**Logs** first, quickly. When you call LogWarning on an ILogger, Microsoft's logging library fans the call out to every registered logging provider. The console provider prints it as before. The OpenTelemetry provider, the Scribe's Copier, takes a LogRecord object from a pool, fills in the timestamp, severity, category, the message template, like "Card declined for order, curly-brace OrderId", the attribute values separately, like OrderId equals 42, and the current trace ID and span ID from the Clipboard. Then the record goes through a batch processor and an exporter, just like spans. Keeping the template separate from the values is structured logging, and it's the logs version of the cardinality idea: the Archive can group every "card declined" message regardless of the order ID. One gotcha: LogRecords are pooled and reused. An exporter must finish with a record inside its Export method and never keep a reference to it afterwards, because the same object will soon be refilled with a different log. Unlike in C, nothing will crash; you'd just silently read the wrong log's data.

Now **sampling**. At ten thousand requests a second with twenty spans each, you'd export two hundred thousand spans a second, and most of them describe boring successes. Sampling keeps a representative fraction. There are two kinds. **Head sampling** decides when a span starts, inside the app, with very little information: just the parent, the trace ID, the name and the starting tags. **Tail sampling** decides after the whole trace is complete, so it can keep every trace that had an error or was slower than two seconds. No single service sees a whole trace, so tail sampling has to happen in the Sorting Office, the Collector, which buffers spans by trace ID for a few seconds and then decides. The catch is that every span of a trace has to reach the **same** Collector instance, so you need load balancing that routes by trace ID.

The built-in head samplers are: AlwaysOn, which keeps everything. AlwaysOff, which keeps nothing, apart from the context-only spans from part seven. TraceIdRatioBased, which keeps a fixed fraction, say ten percent, chosen from the trace ID itself, so every service using the same ratio makes the same choice for the same trace. And ParentBased, which is the default: if there's a parent, copy its sampled flag; if not, ask a root sampler, which by default is AlwaysOn. Here's why parent-based is the default. If service A keeps a trace and service B independently drops its part, the trace has holes. Following the sampled flag in the Stamp keeps whole traces, or nothing.

Three different "no"s are easy to confuse, so let's compare them directly. The first guard is "should I listen to this Reporter?", answered once per source name, from the names you added. If the answer is no, StartActivity always returns null. The second guard is the Selector's decision, made for every span. If it's drop, you get null or a context-only span, depending on the parent. The third guard is the property IsAllDataRequested, checked when a span starts and stops. If it's false, the span object exists but the Desk Clerks never see it, and nothing is exported. So a common misconception is that a non-null Activity will be exported. Actually, non-null only means the object exists; IsAllDataRequested is what tells you it's being recorded.

The **Collector**, the Sorting Office. Why have one, when apps can export straight to the Archive? Because with a Collector, services only need to know "send to localhost port 4317", while the Collector holds the backend's address and credentials. Changing backends means changing one Collector's configuration, not redeploying every service. Batching, retries and sampling happen in one place, and tail sampling becomes possible at all. A Collector is configured with a YAML file that wires components into a pipeline for each signal. **Receivers** take data in, in OTLP or many other formats. **Processors** do things to it in the middle, like limiting memory, batching, editing attributes, or tail sampling. **Exporters** send it on. And **connectors** join pipelines, for example turning spans into request-rate and error-rate metrics. In production, there's usually a Collector **agent** close to each app, and a pool of **gateway** Collectors that all the agents send to. It's written in Go, so you'll configure and run it, not change it.

And the **semantic conventions**, the Dictionary. A few names you'll meet constantly: service dot name on the resource. http dot request dot method, like GET. http dot route, the route template that matched, like slash orders slash curly-brace id. url dot path, the actual path, like slash orders slash 42. http dot response dot status underscore code. error dot type. And the rule that an HTTP server span is named with the method, a space, and the route. In the .NET repositories, these strings live in one file called SemanticConventions dot cs, inside a shared folder, which is linked into each project that needs it. The Annotator sets the name at the **end** of the request, because the route is only known after routing has run. Conventions move through stages, development, then release candidate, then stable, and renaming a stable attribute breaks every dashboard and alert that used it. The HTTP conventions went stable in 2023 with renames, like http dot method becoming http dot request dot method. So instrumentation maintainers treat a name change as a breaking change, and the first question they'll ask about an instrumentation pull request is "which version of the conventions, and is this attribute stable?"

Recap of part eleven. Logs keep using ILogger; the OpenTelemetry provider copies each call into a pooled LogRecord stamped with the trace ID, and exporters must never hold on to one. Head sampling decides at span start; the default ParentBased sampler keeps traces whole; tail sampling needs a Collector that sees the whole trace. Three different guards can stop a span: the listener filter, the Selector, and IsAllDataRequested. The Collector receives, processes and exports in per-signal pipelines, usually as agents plus gateways. And the semantic conventions are the shared Dictionary, where low cardinality and stability are what the maintainers care about.

## Part twelve: the repository, testing, and how to contribute

The core repository's layout follows the three layers. At the top level, three files are worth reading before any code. **AGENTS dot md** has the build and test commands, the architecture, and the conventions; it was written for AI coding agents, and it's the best single orientation page for humans too. **REVIEW dot md** says what pull request reviewers check. **CONTRIBUTING dot md** has the contribution rules. Then global dot json pins the .NET SDK, version 10.0.401. Directory dot Packages dot props holds every package version in one place, which is called central package management, so a project file never says a version itself.

Under the src folder, there's one folder per NuGet package. OpenTelemetry dot Api holds baggage, the propagators and the runtime context. The folder named just OpenTelemetry is the SDK, with subfolders for Trace, Metrics, Logs and Resources, and an Internal folder holding the circular buffer and the background workers. OpenTelemetry dot Extensions dot Hosting holds AddOpenTelemetry and the tiny hosted service. Then come the exporters: OTLP, console, in-memory, Prometheus, and Zipkin, which is deprecated. There's the experimental declarative configuration package. And there's a folder called Shared, holding source files that are **linked** into many projects rather than referenced. Every project has a CHANGELOG file, and a hidden folder called dot publicApi, which lists every public signature. The build fails if your public API doesn't match that file, which is how reviewers spot API changes immediately. The test folder has one test project per package, plus fuzz tests, stress tests and benchmarks. The docs folder has getting-started guides for each signal, which are official walking skeletons. And the examples folder has the RabbitMQ microservice example.

Because you tend to follow every call into its implementation and lose the overall map, here's a depth budget for a first pass: six stops, then stop. One: AGENTS dot md. Two: the getting-started console guide for traces, and run it. Three: the tracer provider's constructor, in TracerProviderSdk dot cs, stopping at the call that registers the listener. Four: the batch export processor, for the drop logic and the defaults, without opening the circular buffer yet. Five: the base exporter and the console exporter, to see what an exporter must do. Six: Baggage dot cs, for the box. Anything else that makes you curious goes on a parking list for the second pass.

Building and testing. The build command is dotnet build on the solution file with the Release configuration, and in Release, warnings are errors. You can run one test project, filter to one test by name, or run only one target framework, which is much faster. That matters because libraries here build for every supported .NET, plus two old targets, netstandard 2.0 and .NET Framework 4.6.2. That's why you'll see blocks of code wrapped in hash-if NET or hash-if NETFRAMEWORK: the same file compiles several times, with different APIs available each time. On your Mac, run tests for net10.0 only. ## Part thirteen: common misconceptions, and the final recap

Let's collect the misconceptions, each as the wrong version, then the correction.

Wrong: OpenTelemetry is a monitoring tool, like Grafana. Right: OpenTelemetry produces and moves telemetry; storing, querying and drawing it is the Archive's job.

Wrong: once OpenTelemetry is installed, everything is traced. Right: only code that calls StartActivity, from a source you added, produces spans. Instrumentation libraries cover frameworks, not your business logic.

Wrong: in .NET you should use OpenTelemetry's Tracer and span classes. Right: use the runtime's ActivitySource and Activity; the OpenTelemetry classes are a shim.

Wrong: the using directive gives your code access to System dot Diagnostics. Right: it only shortens names; access comes from what the project references.

Wrong: OpenTelemetry is middleware in the request pipeline. Right: it's a subscriber, registered with the runtime's static listener machinery, and the runtime calls it.

Wrong: StartActivity always returns a span. Right: it returns null when no listener wants that source, or when the sampler drops a span whose parent is local. That's why every call site writes question-mark-dot.

Wrong: a non-null Activity will be exported. Right: it can be a context-only Activity, with IsAllDataRequested set to false.

Wrong: telemetry is sent while the request waits. Right: ended spans go into a bounded queue, and a background thread exports them; when the queue is full, the newest span is dropped, and the request never waits.

Wrong: the Collector or the backend connects spans from different services. Right: services connect them at run time through the traceparent header. A missing header can't be repaired later.

Wrong: Baggage leaks because AsyncLocal is broken. Right: AsyncLocal works as designed; the leak comes from storing a shared mutable box inside it and writing into the box.

Wrong: Activity's baggage and OpenTelemetry's baggage are the same thing. Right: they're two separate stores, and OpenTelemetry's propagators send OpenTelemetry's.

Wrong: a metric is a list of every measurement. Right: it's an in-memory aggregate per attribute combination, exported periodically, with a default limit of 2000 combinations per metric.

Wrong: the garbage collector will take care of the tracer provider. Right: the garbage collector reclaims memory; it doesn't flush queues or stop threads. Dispose the provider, or lose the last batch.

And now the final recap: the ten key ideas, which are also the teach-back checklist.

One. OpenTelemetry is a vendor-neutral standard, with a specification, semantic conventions and the OTLP wire format, plus libraries and a Collector to produce and move traces, metrics and logs. Storage and display belong to a backend.

Two. In .NET, ActivitySource, Activity, Meter and ILogger are the API, and they live in the runtime. OpenTelemetry .NET is mainly the SDK that subscribes to them. Libraries use only the API; applications add the SDK and exporters.

Three. One span's life: the Reporter checks for a listener, the Selector decides, the Timecard goes on the Clipboard, Dispose stops it, the Desk Clerks get OnEnd, the Mailroom puts it in the Out-Tray, and the Mail Carrier ships batches to the Packer.

Four. No listener, no span: StartActivity can return null, hence question-mark-dot; and a non-null Activity can still be unrecorded.

Five. Propagation: the traceparent Stamp carries the trace ID, the caller's span ID and the sampled flag. Inject on the way out, extract on the way in. Without the header, the trace splits in two.

Six. Ambient context: Activity dot Current and Baggage dot Current belong to the async flow through AsyncLocal. Values flow down, not up. The baggage leak comes from a shared mutable holder.

Seven. Metrics are aggregated in memory per attribute combination, with a default cardinality limit of 2000 and an overflow row, exported every sixty seconds, cumulative by default.

Eight. Backpressure and disposal: when the queue is full, drop the newest and never block; dispose or flush the provider, or lose the last batch.

Nine. Sampling and the Collector: parent-based head sampling keeps traces whole; tail sampling needs a Collector that sees whole traces.

Ten. Semantic conventions are the shared Dictionary. Names like http dot route and span names like "GET slash orders slash curly-brace id" must be low-cardinality and stable, and that's the whole story behind the YARP span-naming discussion.

That's OpenTelemetry from the ground up. The best next step isn't more reading. It's the five-minute console experiment: one source, two spans, the console exporter, and then breaking it on purpose, three ways.
